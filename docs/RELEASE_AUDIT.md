# Предрелизный аудит ChurchCMS

Перед публикацией версии 1.0 выполняется единый локальный аудит:

```bash
php bin/release-audit.php
```

Он проверяет:

- PHP 8.3 или новее;
- обязательные расширения `json`, `openssl`, `pdo`;
- синтаксис всех PHP-файлов репозитория;
- целостность набора миграций;
- регистрацию тем и наличие всех объявленных шаблонов.

Обычный запуск намеренно **не считает производительность пройденной**. GitHub Actions не является эталонным сервером и не должен задавать фиктивные пороги для релиза.

## Что уже закрыто для 1.0

До финального performance gate должны оставаться зелёными существующие release-candidate проверки:

- установка с нуля через web-installer;
- PostgreSQL runtime, backup/restore и schema-changing updater/rollback;
- MySQL migrations/readiness;
- подписанный code-only updater;
- PHP 8.3 lint/runtime/theme checks;
- production deployment profile: Nginx HTTPS, PHP-FPM и фоновые задачи.

Эти проверки подтверждают техническую готовность релизного кандидата, но не заменяют эталонное измерение производительности.

## Финальный запуск 1.0 на эталонном стенде

После реального HTTP load-test передайте его JSON и утверждённый профиль порогов:

```bash
php bin/release-audit.php \
  --performance-result=/path/http-load.json \
  --performance-thresholds=/path/release-thresholds.json
```

В этом режиме дополнительно запускается `tools/performance/release-gate.php`. Если хотя бы один обязательный показатель не проходит порог, весь аудит завершается с ненулевым кодом.

Профиль порогов должен описывать реальное эталонное железо и окружение: CPU, RAM, хранилище, веб-сервер, PHP и СУБД. Значения p50/p95/p99/RPS и допустимой доли ошибок фиксируются только после измерения на выбранном сервере.

## Что не блокирует тег 1.0.0

Следующие задачи не входят в обязательный release gate 1.0 и не должны маскироваться под незавершённость ядра:

- legacy VPDS migration до появления подтверждённого формата экспорта;
- Rutube outbound upload до подтверждённого официального API;
- СМИ2 и News Mail до получения партнёрских спецификаций;
- пилотные внедрения и редакторская обратная связь.

## Порядок перед тегом 1.0.0

1. Ветка релизного кандидата должна быть заморожена для новых функций.
2. Полный CI ветки релиза должен быть зелёным.
3. PostgreSQL и MySQL проверки должны быть зелёными.
4. Выполнить `php bin/release-audit.php`.
5. На зафиксированном эталонном стенде выполнить HTTP load-test.
6. Зафиксировать профиль стенда и утверждённые release thresholds.
7. Запустить аудит повторно с `--performance-result` и `--performance-thresholds`.
8. Проверить создание и восстановление резервной копии на релизном кандидате.
9. Проверить установку с нуля. Проверку обновления выполнять только с реально существующей поддерживаемой предыдущей версии; для первого стабильного релиза не придумывать искусственный источник обновления.
10. Проверить `docs/DEPLOYMENT.md` на выбранном production-подобном сервере.
11. Только после этого создавать тег и релиз `1.0.0`.

До выполнения пункта с эталонным performance gate разрешено готовить release branch/RC, но не финальный тег `1.0.0`.

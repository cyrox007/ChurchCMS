# Предрелизный аудит ChurchCMS

Перед публикацией версии 1.0 выполняется единый локальный аудит:

```bash
php bin/release-audit.php
```

Он проверяет:

- PHP 8.3 или новее;
- обязательные расширения `json`, `openssl`, `pdo`;
- синтаксис всех PHP-файлов репозитория;
- целостность набора миграций;
- регистрацию тем и наличие всех объявленных шаблонов.

Обычный запуск намеренно **не считает производительность пройденной**. GitHub Actions не является эталонным сервером и не должен задавать фиктивные пороги для релиза.

## Что уже закрыто в коде 1.0

До финального performance gate должны оставаться зелёными существующие проверки релизного кандидата:

- установка с нуля через web-installer;
- PostgreSQL runtime, backup/restore и обновление со schema rollback;
- MySQL migrations/readiness;
- подписанный code-only updater;
- PHP 8.3 lint/runtime/theme checks;
- production deployment profile: Nginx HTTPS, PHP-FPM и фоновые задачи;
- приходской/кафедральный и образовательный профили;
- федерация и внешнее распространение;
- внутренний исходящий контур Rutube с безопасной границей официального партнёрского upload-доступа;
- профили СМИ2 и News Mail с валидацией и диагностикой партнёрского подключения;
- импорт из VPDS с dry-run, Media, редиректами, стратегией пользователей и отчётом;
- Media Storage & Optimization;
- браузерный AJAX/UX-аудит Admin Shell.

Эти проверки подтверждают готовность внутреннего кода релизного кандидата, но не заменяют внешнюю и эксплуатационную приёмку.

## Финальный запуск 1.0 на эталонном стенде

После реального HTTP load-test передайте его JSON и утверждённый профиль порогов:

```bash
php bin/release-audit.php \
  --performance-result=/path/http-load.json \
  --performance-thresholds=/path/release-thresholds.json
```

В этом режиме дополнительно запускается `tools/performance/release-gate.php`. Если хотя бы один обязательный показатель не проходит порог, весь аудит завершается с ненулевым кодом.

Профиль порогов должен описывать реальное эталонное железо и окружение: CPU, RAM, хранилище, веб-сервер, PHP и СУБД. Значения p50/p95/p99/RPS и допустимой доли ошибок фиксируются только после измерения на выбранном сервере.

## Что всё ещё блокирует тег 1.0.0

Финальный тег нельзя создавать, пока не закрыты обязательные внешние и эксплуатационные проверки:

- эталонный performance gate с зафиксированным профилем оборудования и реальными порогами;
- официальный партнёрский upload-доступ Rutube и сквозная внешняя приёмка исходящей отправки;
- внешняя проверка партнёрских контуров СМИ2 и News Mail там, где она требует доступа/одобрения партнёра;
- живое пилотное развёртывание на production-подобном сервере;
- ручная проверка основных пользовательских сценариев, мобильного Admin Shell, обновления, backup/restore, внешних каналов и Media lifecycle;
- исправление найденных на пилоте дефектов и повторный прогон затронутых gate-проверок.

Наличие внешней зависимости не означает, что внутренний код можно считать незавершённым, но и не позволяет объявить реальную интеграцию проверенной до фактической приёмки.

## Порядок перед тегом 1.0.0

1. Завершить внутренний функциональный scope 1.0 и его аудит.
2. Выполнить эталонный HTTP load-test на зафиксированном Nginx/PHP-FPM стенде с репрезентативными данными.
3. Зафиксировать профиль стенда и реальные release thresholds.
4. Запустить `php bin/release-audit.php` с `--performance-result` и `--performance-thresholds`.
5. Закрыть обязательные внешние партнёрские приёмки, включая Rutube upload.
6. Развернуть текущий `develop`/кандидат на пилотном production-подобном сервере.
7. Проверить установку с нуля, backup/restore, обновление только с реально существующей поддерживаемой предыдущей версии, Media lifecycle и основные пользовательские сценарии.
8. Исправить дефекты пилота и повторить затронутые проверки.
9. Создать **свежую** финальную release/RC-ветку; старую промежуточную ветку `release/1.0.0-rc1` не переиспользовать.
10. Заморозить релизную ветку для новых функций и получить полностью зелёный CI.
11. Проверить актуальность русскоязычной документации и release notes.
12. Только после этого создавать тег и релиз `1.0.0`.

До прохождения эталонного performance gate, внешних приёмок и живого пилота финальный тег `1.0.0` запрещён.

# Обновления ChurchCMS

Этот документ описывает текущий технический фундамент обновлений. ChurchCMS умеет проверить пакет во внешнем staging и безопасно применить code-only обновление без изменений схемы БД с обязательной резервной копией, healthcheck и автоматическим откатом файлов.

## Формат пакета

Формат `churchcms-update-v1` — это каталог с `manifest.json` и файлами приложения в тех же относительных путях, в которых они должны находиться после будущего применения.

Пример:

```text
churchcms-update/
├── manifest.json
├── core/
│   └── Example.php
└── themes/
    └── default/
        └── ...
```

Минимальный manifest:

```json
{
  "format": "churchcms-update-v1",
  "from_version": "0.1.0-dev",
  "version": "0.1.1",
  "php_min": "8.3",
  "files": [
    {
      "path": "core/Example.php",
      "bytes": 1234,
      "sha256": "..."
    }
  ],
  "deleted_files": []
}
```

## Что проверяется до staging

Пакет отклоняется, если:

- `from_version` не совпадает с установленной версией ChurchCMS;
- целевая версия имеет некорректный формат, совпадает с текущей или ниже текущей;
- пакет требует PHP ниже проектного минимума 8.3 или выше фактически установленной версии PHP;
- набор реальных файлов отличается от `files` в manifest;
- размер или SHA-256 хотя бы одного файла не совпадает;
- присутствует символическая ссылка;
- путь абсолютный, содержит `..`, обратный слеш или другой небезопасный сегмент;
- пакет пытается заменить `config/local.php`, содержимое `storage` или `.git`;
- источник пакета расположен внутри ChurchCMS;
- staging расположен внутри ChurchCMS;
- source и staging вложены друг в друга.

`deleted_files` тоже проходит проверку безопасных путей. Для разрешённого code-only apply такие файлы удаляются через тот же откатываемый файловый сценарий.

## Staging

Техническая команда:

```bash
php bin/update.php stage /абсолютный/путь/к/пакету
```

Путь staging по умолчанию задаётся `operations.update_staging_path` и расположен рядом с каталогом ChurchCMS. Его можно переопределить:

```bash
php bin/update.php stage /tmp/churchcms-update --path=/var/lib/churchcms-updates
```

Сначала пакет полностью проверяется в source-каталоге. Затем manifest и только перечисленный payload копируются во временный staging-каталог, контрольные суммы проверяются повторно, после чего каталог атомарно переименовывается в готовый staging ID.

## Что staging не делает

Staging намеренно не:

- заменяет файлы работающего ChurchCMS;
- запускает миграции;
- удаляет старые файлы;
- меняет `config/local.php` или uploads;
- выполняет healthcheck как проверку уже применённого обновления.

Сетевая загрузка выполняется отдельным шагом до обычного staging.

## Применение code-only обновления

После staging локальный оператор может явно применить пакет:

```bash
php bin/update.php apply <staging-id> \
  --confirm=<staging-id>
```

Staging ID требуется повторить намеренно. До первого изменения ChurchCMS:

1. повторно проверяет manifest, payload, размеры и SHA-256 staging-пакета;
2. отклоняет пакет с файлами под `database/migrations/` или `modules/*/migrations/`;
3. требует `config/app.php` с новой версией приложения;
4. создаёт обычную резервную копию config/uploads/БД;
5. повторно проверяет созданную резервную копию.

При разрешённом code-only apply новые файлы сначала копируются во временные кандидаты рядом с целевыми путями. Старые файлы сохраняются до завершения проверки. Затем ChurchCMS применяет замену/добавление/удаление, проверяет SHA-256 установленных файлов, синтаксис изменённых PHP-файлов через встроенный PHP parser, целевую версию и installation healthcheck.

Если любой шаг после начала замены завершается ошибкой, файловые операции выполняются в обратном порядке: новые файлы удаляются, предыдущие версии возвращаются, удалённые файлы восстанавливаются. Проверенная резервная копия при этом остаётся доступной отдельно.

CI покрывает три сценария:

- успешное code-only обновление с добавлением и удалением файла;
- намеренно повреждённый PHP-пакет с автоматическим rollback;
- пакет с migration-файлом, который отклоняется до создания новой резервной копии и до изменения установки.

## Контракт обратимых миграций

Движок миграций теперь различает обычные и явно обратимые миграции. Для новой миграции, которую в будущем планируется допускать к автоматическому schema-changing обновлению, необходимо реализовать `ChurchCMS\\Core\\ReversibleMigration` и метод `down(PDO $pdo, string $driver)`.

`MigrationRunner::rollback()` принимает только явный список идентификаторов. До первого изменения БД он проверяет весь набор целиком: каждая миграция должна существовать в текущем коде, быть отмечена как применённая и реализовывать обратимый контракт. После этого миграции выполняются в обратном порядке идентификаторов и удаляются из `churchcms_migrations` только после успешного `down()`.

Это фундамент безопасного schema rollback, а не разрешение migration-пакетов в updater. Старые и любые необратимые миграции продолжают блокировать автоматическое применение обновления до появления полного сценария возврата схемы и данных.

## Почему пакеты с миграциями пока запрещены для auto-apply

Текущий логический backup хранит данные и описание текущих таблиц, но не является полным DDL-снимком старой схемы. После schema-changing миграции обычный `restore-db` справедливо откажется восстанавливать данные в несовпадающую схему.

Поэтому ChurchCMS не делает вид, что умеет гарантированно откатывать произвольные миграции. Автоматическое применение пакетов с изменениями схемы останется запрещённым, пока не будет реализован и проверен отдельный механизм возврата старой схемы/совместимого восстановления данных.

Это ограничение не относится к локальному staging: migration-пакет можно проверить и разместить во staging, но команда `apply` остановит его до изменения установленной системы.

Проверка SHA-256 подтверждает целостность файлов относительно манифеста, а цифровая подпись подтверждает происхождение самого манифеста.

## Получение пакета по сети

В `config/local.php` оператор задаёт точный URL подписанного манифеста:

```php
'operations' => [
    'update_release_manifest_url' => 'https://updates.example.org/stable/manifest.json',
],
```

ChurchCMS не принимает URL из браузерной формы. Команда:

```bash
php bin/update.php download
```

сначала получает только `manifest.json`, проверяет его цифровую подпись и только после этого скачивает перечисленный payload с того же HTTPS-origin. Redirects, URL с credentials/query/fragment, частные/локальные/служебные IP и DNS-ответы на такие адреса запрещены. Для доменного имени адрес закрепляется в cURL после проверки DNS, что не позволяет повторному DNS-ответу незаметно увести запрос во внутреннюю сеть.

Манифест ограничен 1 МиБ, отдельный файл — 64 МиБ, весь пакет — 256 МиБ. Каждый файл после загрузки проверяется по размеру и SHA-256 из подписанного манифеста. Временный каталог удаляется и при успехе, и при ошибке; только после полной проверки пакет передаётся обычному `UpdatePackageStager`.

Для сетевой загрузки требуется PHP-расширение cURL. TLS-проверка сертификата не заменяет цифровую подпись релиза: используются оба барьера.

## Admin Shell

Раздел «Система» показывает готовые staging-пакеты без необходимости вводить серверные пути.

Для пакета, который повторно проходит staging-проверку и не содержит migration-файлов, оператор может:

1. отметить явное подтверждение выбранного пакета;
2. нажать «Применить»;
3. получить автоматическое создание/проверку backup перед заменой файлов;
4. получить healthcheck и автоматический файловый rollback при ошибке.

Повреждённые/устаревшие пакеты и пакеты с миграциями отображаются без возможности автоматического применения.

Если `operations.update_release_manifest_url` настроен локально, Admin Shell показывает действие «Получить подписанный пакет». URL не выводится в форму и не принимается от пользователя. Успешная загрузка фиксируется в audit log отдельно от последующего применения.

# Подпись релизных пакетов ChurchCMS

## Зачем нужна подпись

SHA-256 в `manifest.json` подтверждает, что файлы не изменились относительно
самого манифеста. Этого недостаточно для подтверждения происхождения релиза:
злоумышленник мог бы заменить одновременно файл, его SHA-256 и манифест.

ChurchCMS поэтому принимает пакет обновления в staging только после проверки
цифровой подписи манифеста по заранее закреплённому публичному ключу.

Подпись покрывает все поля манифеста, кроме самого объекта `signature`:
версию формата, исходную и целевую версии ChurchCMS, минимальную версию PHP,
список файлов, размеры, SHA-256 и список удалений.

## Разделение ключей

Приватный ключ:

- хранится только у того, кто выпускает релиз;
- не должен находиться в репозитории ChurchCMS;
- не должен копироваться на сайты, которые только устанавливают обновления;
- может находиться на отдельном носителе;
- при использовании зашифрованного PEM пароль передаётся через переменную
  окружения `CHURCHCMS_UPDATE_SIGNING_PASSPHRASE`.

Публичный ключ:

- не является секретом;
- закрепляется на устанавливаемом ChurchCMS через `config/local.php`;
- идентифицируется стабильным `key_id`;
- может существовать параллельно со старым ключом во время ротации.

При пустом списке доверенных публичных ключей ChurchCMS намеренно блокирует
staging и применение релизных пакетов.

## Создание пары ключей

Пример для релизной машины:

```bash
openssl genpkey \
  -algorithm RSA \
  -pkeyopt rsa_keygen_bits:3072 \
  -out /secure/churchcms-release-private.pem

openssl pkey \
  -in /secure/churchcms-release-private.pem \
  -pubout \
  -out /secure/churchcms-release-public.pem
```

Приватный ключ нельзя добавлять в Git, архив релиза или каталог установленного
ChurchCMS.

## Закрепление публичного ключа на установке

В `config/local.php` добавляется публичный ключ релиза:

```php
'operations' => [
    'update_trusted_public_keys' => [
        'release-2026' => <<<'PEM'
-----BEGIN PUBLIC KEY-----
...
-----END PUBLIC KEY-----
PEM,
    ],
],
```

В production публичный ключ должен поступать по отдельному доверенному каналу:
например, вместе с исходной установкой, через управляемую конфигурацию сервера
или после ручной сверки отпечатка.

## Подпись готового манифеста

Сначала формируется обычный `manifest.json` формата
`churchcms-update-v1`, включая SHA-256 всех файлов. Затем выполняется:

```bash
php tools/update-sign.php \
  /absolute/path/to/package/manifest.json \
  /secure/churchcms-release-private.pem \
  release-2026
```

Инструмент:

1. требует абсолютные пути;
2. отказывается использовать приватный ключ внутри репозитория ChurchCMS;
3. формирует однозначное представление манифеста;
4. подписывает его OpenSSL + SHA-256;
5. добавляет объект `signature` с алгоритмом, `key_id` и Base64-подписью.

После подписи нельзя менять ни одно подписанное поле. Если состав пакета
изменился, необходимо пересчитать SHA-256, заново сформировать манифест и
подписать его повторно.

## Проверка на установке

`UpdatePackageStager` проверяет подпись дважды по жизненному циклу:

- перед копированием исходного пакета в staging;
- при каждом `inspect` уже staged-пакета.

`UpdatePackageApplier` всегда вызывает `inspect` перед backup и заменой
файлов. Поэтому подмена манифеста уже после staging также блокирует применение
до изменения установки.

Пакет отклоняется, если:

- подпись отсутствует;
- `key_id` отсутствует в доверенном наборе;
- подпись повреждена или не соответствует манифесту;
- публичный ключ имеет неверный формат;
- OpenSSL недоступен.

Admin Shell показывает `key_id` подтверждённой подписи. Тот же идентификатор
записывается в audit metadata успешного применения обновления.

## Ротация ключей

Безопасная ротация выполняется с перекрытием:

1. добавить новый публичный ключ под новым `key_id`;
2. выпустить релиз, подписанный новым приватным ключом;
3. убедиться, что установки получили новый публичный ключ;
4. после переходного периода удалить старый публичный ключ из доверенного
   списка;
5. больше не выпускать пакеты со старым приватным ключом.

При компрометации приватного ключа его `key_id` нужно немедленно удалить из
доверенного списка установок. Ранее staged-пакеты с этим ключом после удаления
также перестанут проходить повторный `inspect`.

## Что ещё не реализовано

Подпись решает задачу аутентичности пакета, но не выполняет сетевую доставку.
Автоматическая загрузка релиза из удалённого источника остаётся отдельным
инкрементом. Такой источник должен использовать проверенную подпись как
обязательный барьер перед staging независимо от TLS и адреса загрузки.

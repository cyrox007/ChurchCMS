# Организационная модель и федерация ChurchCMS

## Зачем это нужно

ChurchCMS не должна быть CMS только для одного прихода.

Одна и та же кодовая база должна поддерживать самостоятельные сайты:

- прихода;
- кафедрального собора;
- монастыря;
- благочиния;
- епархии;
- митрополии;
- духовной школы/семинарии;
- епархиального отдела, комиссии или другой церковной организации;
- смешанной организации.

Каждая установка остаётся полноценным самостоятельным сайтом и не требует центрального ChurchCMS-сервера.

## Что показал анализ действующих сайтов

При проектировании были просмотрены структуры сайтов Воронежской митрополии/епархии, Борисоглебской, Россошанской и Острогожской, Елецкой, Липецкой, Тамбовской и Мичуринской епархий/митрополий.

На разных сайтах повторяются одни и те же доменные сущности:

- митрополия → епархии → благочиния → приходы/храмы;
- монастыри и подворья;
- кафедральные соборы;
- правящий/викарный архиерей;
- духовенство и назначения;
- благочинные и помощники;
- епархиальные отделы, комиссии, советы и службы;
- руководители подразделений и контактные данные;
- указы, распоряжения, циркуляры и другие официальные документы;
- архиерейское служение;
- новости епархии, благочиний, приходов, монастырей и отделов;
- события, анонсы и календарные материалы;
- образовательные учреждения;
- паломническая деятельность;
- благотворительность/социальное служение;
- СМИ, видео, печатные издания и архивы;
- адреса, телефоны, email, сайты и социальные сети;
- принадлежность конкретного храма/человека/материала к организационному уровню.

Это означает, что ChurchCMS должна хранить структуру и принадлежность как данные, а не зашивать их в меню или тему.

## Локальное организационное дерево

`organization_units` — дерево организаций и подразделений, которыми управляет текущая установка.

Примеры `unit_type`:

- `metropolia`;
- `diocese`;
- `deanery`;
- `parish`;
- `cathedral`;
- `monastery`;
- `chapel`;
- `department`;
- `commission`;
- `council`;
- `educational_institution`;
- `church_organization`.

Список не является закрытым DB enum: новые типы можно добавлять без изменения формата БД.

Каждый `site_key` имеет `organization_site_roots` — организацию, которую представляет сам сайт.

Пример сайта епархии:

```
Липецкая епархия               ← site root
├── 1-е Липецкое благочиние
│   ├── приход A
│   └── приход B
├── Задонское благочиние
├── Отдел образования
├── Молодёжный отдел
└── Паломнический отдел
```

Не все дочерние элементы обязаны управляться этой же установкой.

## Автономные узлы

Каждая установка получает постоянный публичный `federation.instance_id`.

Узел самостоятельно хранит:

- пользователей;
- права;
- настройки;
- темы;
- свои публикации;
- свои страницы;
- свои медиа;
- локальную организационную структуру;
- локальные журналы;
- резервные копии.

Отсутствие сети или вышестоящего ChurchCMS не блокирует обычную работу.

## Федеративная связь

`organization_federation_links` описывает доверенную техническую связь между независимыми установками.

Отношение задаётся относительно локального узла:

- `parent` — удалённый ChurchCMS представляет вышестоящую организацию;
- `child` — удалённый ChurchCMS представляет нижестоящую организацию;
- `peer` — равноправный партнёр.

Примеры:

```
сайт прихода --parent--> сайт благочиния
сайт благочиния --parent--> сайт епархии
сайт епархии --parent--> сайт митрополии
сайт епархии <--peer--> сайт соседней епархии
сайт епархии --child--> сайт семинарии
```

Федеративная связь не меняет автоматически `parent_id` локального дерева.

## Иерархия не равна доверию

Церковное подчинение — организационный факт.

Доступ к данным другого сайта — техническое доверие.

Поэтому:

- епархия не получает пароль администратора приходского сайта;
- митрополия не получает автоматическое право изменять епархиальный сайт;
- подключённый приход сам определяет, какие материалы отдавать вверх;
- получение материалов сверху также ограничивается scopes;
- отключение связи не удаляет локальные материалы.

## Направления обмена

Федерация должна поддерживать независимо:

### Снизу вверх

Например приход → благочиние → епархия:

- новости;
- события;
- богослужения;
- данные храма;
- публичные сведения о духовенстве;
- фото/видео с разрешёнными вариантами;
- статистические/справочные данные при наличии отдельного scope.

### Сверху вниз

Например епархия → благочиние/приход:

- официальные документы;
- указы/распоряжения;
- общеепархиальные события;
- обращения архиерея;
- методические материалы;
- объявления;
- рекомендуемые публикации.

### Между равными узлами

- выбранные новости;
- совместные события;
- публикации проектов;
- документы/материалы совместных комиссий.

## Владение контентом

У любого синхронизированного объекта должен сохраняться canonical owner:

- исходный `instance_id`;
- исходный public ID;
- canonical URL;
- время последнего изменения источника.

Агрегатор может кешировать/проецировать данные, но не должен незаметно становиться их владельцем.

Локальная копия и remote projection — разные состояния.

## Discovery

Каждый готовый узел публикует:

```
GET /api/v1/federation/meta
```

Ответ содержит только безопасную публичную информацию:

- protocol version;
- `instance_id`;
- `site_key`;
- профиль;
- public ID, тип и название корневой организации;
- поддерживаемые capability протокола.

Токены и внутренние DB ID не выдаются.

## Pairing и credentials

Сам discovery не создаёт доверия.

Будущий pairing wizard должен:

1. получить federation metadata;
2. показать оператору, с каким узлом устанавливается связь;
3. явно выбрать `parent/child/peer`;
4. выбрать inbound/outbound scopes;
5. обменяться/активировать credential безопасным способом;
6. сохранить remote credential только в зашифрованном виде;
7. позволить в любой момент отключить или удалить связь.

До появления wizard связь может существовать на уровне API/операторских инструментов, но plaintext token не должен храниться в БД или журнале.

## RBAC по организационной области

Для организационных областей используется существующий `admin_role_scopes`.

Пример:

```
scope_type = organization
scope_key  = <public-id-благочиния>
```

Если у назначения роли нет scope-записей, право считается глобальным. Если у назначения есть scope-записи, оно действует только в явно совпавшей области текущего сайта.

Organization scope наследуется вниз по локальному организационному дереву: право на благочиние действует на его приходы и другие дочерние узлы. Оно не наследуется вверх на епархию и не распространяется на соседние благочиния, отделы или другие ветки.

`OrganizationAccessService` централизует эту проверку. Admin Shell использует его для списка, создания, редактирования, перемещения, архивирования и восстановления структуры. Пользователь не может переместить доступный узел в недоступную ветку или изменить родителя, который находится выше его границы доступа.

Суперадминистратор сохраняет глобальный доступ независимо от scope-записей.

PostgreSQL smoke-проверка создаёт ограниченное назначение роли и подтверждает наследование вниз, запрет доступа к root/соседней ветке и выбор единственной границы как родителя по умолчанию.

## Связь с будущими модулями

Следующие сущности должны уметь ссылаться на organization unit:

- Person / должности / назначения;
- Publications;
- Pages;
- Events;
- Worship;
- Media/Galleries;
- Documents;
- Departments/commissions;
- Shrines;
- educational programs.

Это позволит одному и тому же модулю работать и на приходе, и на благочинии, и на епархии.

Для Publications foundation уже реализован: `owner_organization_public_id`
ссылается на stable public ID локальной organization unit в том же `site_key`.
Новый draft по умолчанию принадлежит корневой организации сайта. Сервис не
разрешает выбрать организацию другого сайта или архивный узел. Public и partner
API возвращают `organization_owner_id`, чтобы агрегатор сохранял canonical
источник материала. Старые строки без доступного site root временно остаются
nullable до явного назначения владельца.

Pages используют тот же invariant `(site_key, owner_organization_public_id)`.
Новая страница получает site root владельцем, а domain service позволяет
назначить активную локальную organization unit. Public API страниц возвращает
stable `organization_owner_id`, `parent_id` и canonical `path`, не раскрывая
внутренние DB ID. Выбор владельца в Admin Shell, публичный HTML и
organization-scoped RBAC остаются следующим вертикальным срезом Pages.

## Управление структурой в Admin Shell

Раздел «Структура» доступен пользователю с правом `organizations.manage`.

Он позволяет:

- видеть единое дерево текущего `site_key`;
- создавать дочернюю организацию или подразделение;
- выбирать известный тип организации;
- менять название, краткое/официальное название, описание и порядок;
- менять родителя;
- менять slug с автоматическим пересчётом путей потомков;
- архивировать и восстанавливать поддерево.

Hard-delete через обычный интерфейс отсутствует. Это намеренно сохраняет стабильные public ID для будущих ссылок People/Documents/Publications и federation.

Корневая организация сайта защищена от архивирования и перемещения под другого родителя.

Admin UI применяет `organizations.manage` вместе с organization scope. Глобальное назначение роли видит всё дерево, ограниченное назначение — только свою границу и её потомков.

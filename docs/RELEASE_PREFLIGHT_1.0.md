# Финальная предрелизная подготовка ChurchCMS 1.0

Этот документ описывает только оставшиеся действия перед тегом `1.0.0`. Внутренний кодовый scope версии 1.0 считается закрытым на `develop`; нижеперечисленные пункты требуют внешнего доступа, эталонного стенда или живого пилота.

## 1. Зафиксировать исходную точку

Перед началом внешней приёмки:

```bash
git fetch origin
git checkout develop
git pull --ff-only origin develop
git rev-parse HEAD
php bin/release-audit.php
```

SHA кандидата записывается в протокол приёмки. Во время измерений и живого пилота новые функции в кандидат не добавляются.

## 2. Эталонный performance gate

На отдельном production-подобном стенде зафиксировать:

- модель и число CPU;
- объём RAM;
- тип и объём хранилища;
- ОС;
- Nginx;
- PHP и параметры PHP-FPM;
- СУБД и её версию;
- число PHP-FPM workers;
- состояние page cache;
- параметры benchmark-набора.

Подготовить одноразовую тестовую базу и репрезентативный набор:

```bash
php tools/performance/seed.php \
  --site=default \
  --publications=10000 \
  --comments=30000 \
  --reset \
  --confirm=benchmark-fixture-default

php tools/performance/query-plan.php
php tools/performance/benchmark.php --iterations=200
```

Полный HTTP-сценарий:

```bash
php tools/performance/http-load.php \
  --base=http://127.0.0.1:8080 \
  --requests=10000 \
  --concurrency=50 \
  --warmup=100 \
  --slug=benchmark-000001 \
  --comment-every=100 \
  --comment-slugs=10000 \
  > /tmp/churchcms-http-load.json
```

После измерения сформировать отдельный JSON с утверждёнными порогами. Порог нельзя придумывать заранее или подгонять ради зелёного результата.

Финальная проверка:

```bash
php bin/release-audit.php \
  --performance-result=/tmp/churchcms-http-load.json \
  --performance-thresholds=/path/release-thresholds.json
```

Сохраняются оба JSON-файла и описание железа.

## 3. Media Storage на реальном S3-compatible backend

На пилотном стенде:

1. настроить отдельный тестовый bucket;
2. загрузить новые JPEG/PNG/WebP и крупные исходники;
3. убедиться, что SHA-256 дедупликация не создаёт второй blob;
4. запустить dry-run архивирования;
5. перенести ограниченную тестовую партию;
6. убедиться, что локальная копия удаляется только после проверки удалённого объекта;
7. открыть старую публикацию после удаления локального blob;
8. подтвердить автоматическое восстановление и повторную проверку SHA-256;
9. проверить очистку пересоздаваемых производных;
10. проверить отчёт занимаемого места и прогноз заполнения.

Ни один уникальный оригинал не удаляется вручную во время приёмки.

## 4. Rutube

До тега требуется официальный партнёрский машинный upload-контракт.

После получения доступа:

- реализовать конкретный `RutubeUploadTransport` только по подтверждённой официальной спецификации;
- не использовать скрытые browser endpoint Rutube Studio;
- проверить видео допустимого формата и размера;
- проверить permanent/retryable ошибки;
- проверить очередь и dead-letter;
- подтвердить реальное появление видео в целевом аккаунте;
- сохранить идентификатор тестовой отправки и результат приёмки.

Если официальный машинный upload-доступ не предоставлен, статус остаётся `rutube_partner_upload_api_required`; интеграцию нельзя объявлять сквозно проверенной.

## 5. СМИ2

До тега требуется партнёрское подтверждение канала.

Проверить:

- доступность `/feeds/smi2.xml` с публичного пилотного домена;
- полный текст, даты, URL и изображения;
- отсутствие ошибок встроенного валидатора;
- включение/исключение публикаций через Admin Shell;
- target-specific overrides;
- появление материалов на стороне партнёра или письменное подтверждение принятого контракта.

## 6. Новости Mail

После одобрения партнёром:

- проверить `/feeds/news-mail.xml` с публичного пилотного домена;
- проверить полный текст, даты, URL и изображения;
- проверить встроенный валидатор;
- проверить target-specific overrides;
- выполнить сквозную приёмку по фактическому партнёрскому контракту.

Не считать технический RSS автоматически официальным форматом партнёра без их подтверждения.

## 7. VPDS

На копии реального legacy-экспорта:

```bash
php bin/vpds-import.php --manifest=/path/export.json --dry-run
```

Проверить отчёт до реального импорта:

- публикации;
- Media и контрольные суммы;
- redirects;
- пользователей;
- битые ссылки;
- отсутствующие Media;
- конфликты и повторный запуск.

После успешного dry-run выполнить импорт на одноразовом пилотном стенде и повторить команду, чтобы подтвердить отсутствие дублей.

## 8. Живой пилот

Пилот разворачивается с текущего зафиксированного кандидата на production-подобном сервере.

Обязательные сценарии:

- установка с нуля;
- вход администратора и RBAC;
- публикация, редактирование, снятие и отложенная публикация;
- страницы, меню, поиск и SEO;
- Media, галереи и документы;
- комментарии и модерация;
- приходской/соборный профиль;
- образовательный профиль;
- федерация;
- внешние каналы;
- RSS/Rambler/СМИ2/Новости Mail;
- мобильный Admin Shell;
- AJAX-действия без полной перезагрузки там, где это предусмотрено;
- backup;
- restore на отдельную тестовую БД;
- обновление с реально поддерживаемой предыдущей версии;
- Media lifecycle и восстановление из архива;
- журнал ошибок и ротация.

Все найденные дефекты фиксируются до создания финальной release-ветки.

## 9. После исправлений пилота

Если код менялся:

```bash
php bin/release-audit.php \
  --performance-result=/path/http-load.json \
  --performance-thresholds=/path/release-thresholds.json
```

Повторяются затронутые smoke/RC-проверки. При изменениях производительного пути повторяется benchmark.

## 10. Финальная release-ветка

Только после закрытия пунктов 2–9 создаётся новая ветка от актуального `develop`.

Старую `release/1.0.0-rc1` не переиспользовать.

Рекомендуемое имя:

```text
release/1.0.0-rc-final
```

В этой ветке запрещены новые функции. Допускаются только блокирующие исправления релиза, после которых повторяются соответствующие проверки.

## 11. Тег и релиз

Тег `1.0.0` создаётся только при одновременно выполненных условиях:

- весь CI финальной release-ветки зелёный;
- performance gate пройден;
- Rutube/СМИ2/Новости Mail прошли требуемую внешнюю приёмку;
- реальный S3-compatible Media archive проверен;
- живой пилот пройден;
- блокирующих дефектов нет;
- backup/restore проверены;
- документация и release notes актуальны.

До этого момента состояние проекта — `release candidate`, а не стабильный релиз.

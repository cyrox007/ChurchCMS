# Внешние каналы

Модуль `social` реализует независимую от конкретного провайдера подсистему внешних каналов.

Один и тот же контракт используется для социальных сетей, мессенджеров, видеоплатформ и будущих интеграций.

## Почему список провайдеров открыт

Приход, епархия или духовная школа могут использовать разные площадки:

- VK;
- Telegram;
- MAX;
- Одноклассники;
- Дзен;
- YouTube;
- Rutube;
- региональные и епархиальные площадки;
- будущие сервисы.

Поэтому `provider` — это проверяемый открытый идентификатор, а не enum в БД. Сторонний модуль может зарегистрировать новый адаптер без изменения ядра и схемы данных.

## Возможности адаптера

Адаптер объявляет только реально поддерживаемые возможности:

```text
publish.text
publish.link
publish.image
publish.video
remote.update
remote.delete
import.posts
import.video
sync.webhook
sync.polling
```

Административный интерфейс и фоновые обработчики не должны предполагать наличие функции, которую адаптер не объявил.

## Мастер подключения в Admin Shell

Раздел «Внешние каналы» показывает зарегистрированные адаптеры и уже сохранённые подключения.

Для безопасного создания подключения адаптер должен дополнительно реализовать `ChannelConnectionTester`. Последовательность такая:

1. оператор выбирает адаптер;
2. вводит название, идентификатор канала и секрет;
3. ChurchCMS вызывает `testConnection()` до записи в БД;
4. при неудачной проверке секрет не сохраняется;
5. при успешной проверке секрет шифруется через `SecretVault` и только затем создаётся `social_connections`;
6. открытый секрет после этого не выводится в Admin Shell и не попадает в audit metadata.

Адаптеры без безопасной проверки видны как недоступные для мастера, пока не реализуют этот контракт.

## Исходящая публикация

```text
Публикация готова
        |
редактор выбирает внешние каналы
        |
создаются записи очереди
        |
фоновый отправщик
        |
адаптер провайдера
        |
сохраняются внешний ID, статус и ошибка
```

Медленная или недоступная внешняя платформа не должна замедлять публичный сайт.

В редакторе уже сохранённой публикации оператор с правом `social.publish` видит только включённые подключения с разрешённым исходящим направлением. Выбранные подключения сохраняются в `publication_social_posts` со статусом `idle` и не отправляются из HTTP-запроса.

При обычной публикации материала выбранные `idle`-записи переводятся в `pending`. При отложенной публикации то же действие выполняет `PublicationScheduleWorker` в момент фактического перехода материала в published. Снятая в редакторе галочка отключает соответствующую outbox-запись.

Для каждого выбранного подключения можно задать отдельный текст длиной до 5000 символов. Он хранится в `publication_social_posts.custom_text` и передаётся только соответствующему адаптеру. Если поле пустое, отправщик использует короткое описание публикации, а при его отсутствии — заголовок. Текст невыбранного канала игнорируется. При снятии канала сохранённый текст не уничтожается, поэтому настройку можно восстановить при повторном выборе.

Если к уже опубликованному материалу добавить новый канал, сохранение редактора переводит только новые `idle`-записи в очередь. Уже отправленные `sent`-записи автоматически повторно не отправляются.

После исчерпания автоматических попыток запись получает состояние `failed` и остаётся в dead-letter разделе Admin Shell. Оператор с `social.publish` может вручную вернуть её в очередь только если само подключение остаётся активным для исходящей отправки, а исходная публикация всё ещё публична. Ручной retry сбрасывает счётчик попыток и предыдущую ошибку и переводит запись в `pending`; сетевой запрос по-прежнему выполняет только фоновый worker. Текст ошибки в Admin Shell всегда экранируется.


## Входящий поток

```text
webhook или polling провайдера
        |
адаптер нормализует ответ
        |
ChannelInboundItem
        |
external_channel_items
        |
проверка оператором
        |
игнорировать / связать / импортировать как черновик
```

По умолчанию входящий материал требует ручной проверки.

### Webhook

Для push-доставки адаптер объявляет capability `sync.webhook` и реализует `ChannelWebhookAdapter`.

Публичный маршрут имеет вид:

```text
POST /api/v1/external-channels/{connectionPublicId}/webhook
```

ChurchCMS принимает webhook только для существующего активного подключения с включённым входящим направлением. До разбора payload выполняются следующие проверки:

1. загружается точное исходное тело HTTP-запроса размером не более 1 МиБ;
2. заголовки нормализуются без изменения их значений;
3. секрет подключения расшифровывается только внутри webhook-сервиса;
4. адаптер обязан подтвердить подпись или общий секрет в `verifyWebhook()`;
5. только после успешной проверки вызывается `receiveWebhook()`;
6. нормализованные `ChannelInboundItem` записываются в общую review-очередь.

Нельзя вычислять подпись по повторно сериализованному JSON: подпись проверяется по исходным байтам `rawBody`. Для HMAC-SHA256 и сравнения shared secret доступен `ChannelWebhookSignature`, использующий `hash_equals()`.

Адаптер может вернуть собственный успешный 2xx acknowledgement через `ChannelWebhookResult`. Ошибки наружу обезличены как `webhook_rejected`; внутреннее описание пишется только в серверный журнал.



Admin Shell показывает только нормализованные поля `ChannelInboundItem`: заголовок, обычный текст, тип, внешний ID и canonical URL. Сырой `payload_json` в шаблон не передаётся. Оператор может:

- исключить объект из очереди без импорта;
- связать объект с уже существующей публикацией ChurchCMS по её публичному ID;
- импортировать объект в новый черновик.

Привязка к существующей публикации требует `publications.read` и дополнительно проверяет organization scope самой публикации. Импорт требует `publications.create`; список организаций-владельцев формируется Publications-модулем только из активных организаций, доступных текущему оператору. Переданный вручную ID чужой организации повторно проверяется на сервере и отклоняется.

Новый материал всегда создаётся в состоянии `draft`. Внешний `bodyText` проходит через `HtmlSanitizer::fromPlainText()`, поэтому даже разрешённые HTML-теги из внешнего текста остаются обычным текстом и не получают доверенный статус.

## Источник истины

Официальная публикация ChurchCMS является источником истины для сайта.

Во внешних каналах допустимы материалы, которых нет на сайте. Изменение внешнего объекта никогда не должно молча перезаписывать официальную публикацию.

## Защита от циклов

Для входящего элемента сохраняются:

- подключение;
- внешний ID;
- fingerprint;
- внешние даты изменения;
- canonical URL;
- связанная публикация ChurchCMS.

Пара «подключение + внешний ID» уникальна. Это позволяет распознавать уже известный объект при последующей двусторонней синхронизации.

Smoke-проверка фиксирует дополнительные инварианты: повторное получение того же remote ID не создаёт вторую запись, обновление remote-объекта не сбрасывает уже установленную связь с публикацией, а обработка входящего объекта сама по себе не создаёт обратную исходящую публикацию. Даже при повторном явном выборе одного внешнего канала для одной публикации действует уникальность пары «publication + connection».

## Безопасность

- секреты шифруются в состоянии покоя через AES-256-GCM;
- ключ шифрования создаётся при установке и хранится только в локальной конфигурации;
- открытые credentials не выводятся в публичный API и шаблоны;
- мастер подключения не сохраняет секрет до успешной проверки адаптером;
- HTTP-клиент адаптеров требует HTTPS;
- webhook-адаптеры обязаны реализовать `ChannelWebhookAdapter` и подтвердить подпись или секрет до разбора события;
- подпись webhook проверяется по исходным байтам тела запроса, а не по повторно собранному JSON;
- сырой внешний payload нельзя напрямую выводить как доверенный HTML.

## Видео

Видео является отдельным видом входящего и исходящего контента.

Контракт поддерживает видео, но загрузка бинарных файлов и перекодирование относятся к Media-подсистеме. Адаптеры YouTube/Rutube могут сначала работать с метаданными и ссылками, а позже — с локальными Media-ресурсами и возобновляемой загрузкой.

## Встроенные адаптеры

### MAX

Встроенный адаптер `max` использует актуальный домен `platform-api2.max.ru`.

Для подключения оператор указывает:

- access token бота как секрет подключения;
- числовой `chat_id` канала или группового чата как идентификатор канала.

Токен передаётся только в заголовке `Authorization` и никогда не добавляется в URL. Мастер проверяет токен через `GET /me`, затем получает `GET /chats/{chatId}` и разрешает подключение только если бот остаётся активным участником канала или группового чата.

Исходящая публикация выполняется через `POST /messages?chat_id=...`. Текст отправляется без разметки, canonical URL добавляется в конец при необходимости, итог ограничивается 4000 символами. В тело запроса явно передаются обязательные для текущего API поля `attachments` и `link`.

Для production входящего потока MAX используется Webhook. При создании inbound-подключения ChurchCMS сначала сохраняет его локально выключенным, строит публичный endpoint из канонического HTTPS URL сайта и вызывает `POST /subscriptions`. В подписку входят события `message_created` и `message_edited`.

Webhook-secret не хранится отдельным открытым полем: он детерминированно выводится через HMAC-SHA256 из bot token и публичного ID подключения. MAX передаёт его в `X-Max-Bot-Api-Secret`, а ChurchCMS проверяет через constant-time сравнение до разбора JSON. Только после успешной удалённой подписки локальное подключение становится активным. Если регистрация отклонена, незавершённая локальная запись удаляется.

Для inbound MAX требуется канонический `syndication.site_url` по HTTPS без нестандартного порта; outbound-only подключение не требует webhook и продолжает работать на локальном стенде. MAX требует стандартный HTTPS/443 endpoint.

Метод `GET /updates` и parser marker-based cursor сохранены как явный dev/fallback инструмент, но production adapter больше не объявляет capability `sync.polling`, поэтому общий worker ChurchCMS не запускает Long Polling одновременно с активной Webhook-подпиской. Вложения сохраняются как безопасные метаданные без автоматического скачивания бинарных файлов.

### VK

Встроенный адаптер `vk` работает с VK API 5.199.

Для подключения оператор указывает:

- пользовательский access token как секрет подключения;
- числовой ID сообщества или короткий адрес сообщества как идентификатор канала.

Мастер разрешает подключение только если `groups.getById` подтверждает сообщество и текущий пользователь имеет уровень редактора или администратора. Для публикации используется `wall.post` с отрицательным `owner_id`, `from_group=1` и детерминированным `guid`, чтобы повтор worker после неопределённого сетевого результата не создавал дубль записи.

Входящий поток использует `wall.get` с `filter=owner`. Курсор ChurchCMS хранит пару «время изменения + ID поста»: это позволяет принимать как новые, так и отредактированные записи, пока они остаются в просматриваемом свежем окне стены. В review-очередь попадают только записи нужного сообщества.

Фото, видео, документы и ссылки нормализуются как метаданные. Бинарные файлы автоматически не скачиваются. Для фото сохраняется URL наибольшего доступного размера, если VK вернул его в ответе.

Access token отправляется в теле POST-запроса, а не в URL.

### Telegram

Встроенный адаптер `telegram` использует Telegram Bot API и регистрируется автоматически.

Для подключения оператор указывает:

- bot token из BotFather как секрет подключения;
- числовой `chat_id` или публичное имя вида `@channel_name` как идентификатор канала.

Мастер проверяет токен через `getMe` и целевой чат через `getChat`. Исходящая публикация выполняется методом `sendMessage`; текст отправляется как обычный UTF-8 без `parse_mode`, а canonical URL публикации добавляется в конец, если его ещё нет. Итог ограничивается 4096 символами.

Входящий поток первой версии использует `getUpdates` через общий polling worker ChurchCMS. Обрабатываются `message`, `edited_message`, `channel_post` и `edited_channel_post`, но в review-очередь попадают только сообщения конкретного `targetRef`. Cursor хранит последний `update_id`, включая отфильтрованные чужие чаты, чтобы polling не зацикливался.

Для фото, видео и документов сохраняются только безопасные метаданные Telegram (`file_id`, MIME/размеры/длительность при наличии); бинарные файлы автоматически не скачиваются. Повторная редакция того же сообщения получает тот же remote ID и обновляет существующий inbound-объект.

Telegram допускает либо `getUpdates`, либо webhook для одного бота одновременно. Встроенный адаптер пока использует polling; общий защищённый webhook-контракт ChurchCMS уже существует и может быть подключён отдельным Telegram-инкрементом без изменения inbox/outbox модели.

Планируемая первая группа:

- Telegram;
- VK;
- MAX;
- YouTube;
- Rutube.

Другие интеграции могут поставляться отдельными модулями и регистрироваться через `ChannelAdapterRegistry`.

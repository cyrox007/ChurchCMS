# SDK адаптеров внешних каналов

Этот документ описывает минимальный контракт для встроенных и сторонних адаптеров ChurchCMS.

Цель адаптера — преобразовать особенности конкретной платформы в общий поток ChurchCMS:

```text
подключение
    |
проверка настроек
    |
outbound / polling / webhook
    |
ChannelOutboundItem / ChannelInboundItem
    |
общие очереди, retry, review и audit ChurchCMS
```

Адаптер не должен создавать собственную параллельную очередь публикаций, хранить открытые секреты или обходить общий review/import процесс.

## Базовый интерфейс

Каждый провайдер реализует `ChannelAdapter`.

Обязательные методы:

- `providerId()` — стабильный машинный идентификатор;
- `label()` — название для Admin Shell;
- `capabilities()` — только реально поддерживаемые возможности;
- `publish()` — исходящая публикация;
- `pull()` — polling входящих данных.

Если направление не поддерживается, метод всё равно остаётся частью базового интерфейса, но адаптер не должен объявлять соответствующую capability и должен вернуть понятную ошибку/пустой результат.

Идентификатор провайдера проходит через `SocialProvider::normalize()`. Нельзя менять его после того, как реальные подключения уже сохранены.

## Capabilities

Используйте константы `ChannelCapability`:

- `publish.text`;
- `publish.link`;
- `publish.image`;
- `publish.video`;
- `remote.update`;
- `remote.delete`;
- `import.posts`;
- `import.video`;
- `sync.webhook`;
- `sync.polling`.

Admin Shell и серверная проверка направления опираются именно на этот список. Нельзя объявлять capability «на будущее», если реализация ещё не готова.

Для исходящего режима нужна хотя бы одна `publish.*` capability.

Для входящего режима нужна хотя бы одна `import.*` capability вместе с `sync.polling` или `sync.webhook`.

## Проверка подключения

Адаптер, который должен создаваться через стандартный мастер, реализует `ChannelConnectionTester`.

`testConnection()` вызывается до сохранения секрета и должен проверить как минимум:

- корректность `targetRef`;
- действительность credentials, если платформа их требует;
- доступ к указанному каналу/сообществу;
- достаточные права для включаемого сценария.

Проверка не должна менять данные у провайдера. Удалённая регистрация webhook относится к отдельному этапу activation.

Сообщение `ChannelConnectionTestResult` предназначено для безопасного операторского статуса. Не возвращайте туда access token, сырые HTTP-заголовки или полный ответ API с чувствительными данными.

## Секреты

Обычный адаптер получает credentials в открытом виде только внутри короткого вызова адаптера. В БД они хранятся через `SecretVault`.

Правила:

- не добавлять токены в URL, если API допускает header/body;
- не писать токены в audit metadata, exception message или шаблон;
- не сохранять вторую копию credentials в `settings_json`;
- не возвращать credentials из публичного API;
- ошибки внешнего API сокращать и очищать от управляющих символов.

Публичные API без credentials должны реализовать `ChannelCredentialsOptional`. Такой адаптер обязан явно отклонять случайно введённый секрет, а не молча его игнорировать.

## HTTP

Для сетевых запросов используйте `ChannelHttpClient`.

Production-реализация `NativeHttpClient`:

- требует HTTPS;
- не следует redirects;
- ограничивает connect/total timeout;
- использует только HTTPS-протокол;
- не требует внешней runtime-библиотеки.

Конструктор адаптера рекомендуется принимать `ChannelHttpClient` с `new NativeHttpClient()` по умолчанию. Это позволяет smoke-тесту подставить детерминированный клиент без реальной сети.

Пример:

```php
public function __construct(
    private readonly ChannelHttpClient $http =
        new NativeHttpClient(),
) {
}
```

## Исходящая публикация

`publish()` получает:

- `SocialConnection`;
- расшифрованные credentials;
- нормализованный `ChannelOutboundItem`.

Адаптер должен:

1. проверить собственные ограничения;
2. выполнить один логический внешний publish;
3. вернуть `ChannelPublishResult`;
4. при успехе сохранить внешний ID, если провайдер его отдаёт;
5. не делать собственный retry.

Retry и dead-letter выполняет `ChannelOutboundDispatcher`.

Если API поддерживает идемпотентный ключ, используйте детерминированное значение из `connection.publicId + sourceId`, чтобы повтор после неопределённого сетевого результата не создавал дубликат.

Не выполняйте сетевую отправку непосредственно из Admin-контроллера.

## Polling

Для polling объявите:

- одну из `import.posts` / `import.video`;
- `sync.polling`.

`pull()` получает сохранённый cursor и лимит.

Cursor должен быть:

- компактным;
- детерминированным;
- достаточным для повторного запуска;
- устойчивым к одинаковым timestamp.

Если провайдер отдаёт пагинацию, адаптер обязан листать данные до сохранённой точки или явно завершиться ошибкой при превышении безопасного окна. Нельзя молча передвигать cursor через непринятые объекты.

Каждый внешний объект преобразуется в `ChannelInboundItem`.

Минимально полезные поля:

- стабильный `remoteId`;
- `kind`;
- обычный текст;
- canonical URL, если существует;
- внешняя дата публикации;
- дата изменения, если существует;
- безопасные media metadata;
- минимальный payload, необходимый для диагностики и повторной идентификации.

Не помещайте в payload access tokens, cookies или полный HTTP-ответ без необходимости.

## Webhook

Для webhook адаптер:

1. объявляет `sync.webhook`;
2. реализует `ChannelWebhookAdapter`.

ChurchCMS передаёт в `verifyWebhook()` точные исходные байты тела и нормализованные заголовки.

Порядок обязателен:

```text
raw body
    |
verifyWebhook()
    |
receiveWebhook()
    |
ChannelInboundItem
    |
review queue
```

Нельзя разбирать и тем более сохранять событие до успешной проверки подписи.

Для HMAC-SHA256/shared secret используйте `ChannelWebhookSignature`, чтобы сравнение выполнялось через `hash_equals()`.

`receiveWebhook()` возвращает `ChannelWebhookResult`. Провайдер может требовать собственный 2xx response body/content type.

## Удалённая активация webhook

Если провайдер требует предварительно зарегистрировать callback URL, дополнительно реализуйте `ChannelConnectionActivator`.

Последовательность ChurchCMS:

1. локальная проверка;
2. временное сохранение подключения выключенным;
3. построение HTTPS webhook URL;
4. `activateConnection()`;
5. включение локального подключения только после успешной удалённой регистрации;
6. удаление незавершённой локальной записи при ошибке.

Так работает production lifecycle MAX.

## Регистрация адаптера

Встроенный адаптер подключается в runtime модуля `social`:

1. файл добавляется в список `require_once`;
2. класс импортируется;
3. экземпляр регистрируется через `ChannelAdapterRegistry::register()`.

Сторонний модуль может зарегистрировать свой адаптер в собственном `boot()`, если модуль загружается вместе с ChurchCMS runtime.

Повторный provider ID запрещён реестром.

## Что проверять в CI

Для каждого встроенного адаптера нужен отдельный smoke без реальной сети.

Минимальный набор:

- runtime registration;
- корректный provider ID и capabilities;
- успешный и неуспешный `testConnection()`;
- точные параметры внешнего HTTP-вызова;
- нормализация inbound;
- cursor и пагинация;
- фильтрация чужого target/channel;
- отсутствие outbound у inbound-only адаптера;
- корректный remote ID/URL для outbound;
- ограничения длины/формата платформы;
- отсутствие credentials в URL/ошибках;
- идемпотентность там, где она поддерживается;
- webhook signature до parse/store;
- регрессия общего External Channels pipeline.

Smoke не должен зависеть от реального аккаунта провайдера или сети.

## Чего адаптер делать не должен

- обходить `SocialConnectionService`;
- самостоятельно расшифровывать данные из БД вне вызова общего сервиса/worker;
- публиковать из HTTP-запроса Admin Shell;
- самостоятельно реализовывать retry/dead-letter вместо общей очереди;
- автоматически импортировать внешний контент как published;
- доверять внешнему HTML;
- скачивать большие бинарные файлы без Media pipeline;
- объявлять upload capability до реализации устойчивой загрузки и повторного продолжения;
- смешивать polling и webhook одновременно, если провайдер считает их взаимоисключающими.

## Шаблон нового адаптера

Рекомендуемый минимальный порядок работы:

1. создать `<Provider>ChannelAdapter`;
2. реализовать `ChannelAdapter + ChannelConnectionTester`;
3. объявить только готовые capabilities;
4. добавить fake `ChannelHttpClient` в smoke;
5. проверить connection setup;
6. добавить outbound или inbound по одному вертикальному сценарию;
7. добавить pagination/cursor;
8. при необходимости добавить webhook и activation;
9. зарегистрировать адаптер;
10. обновить русскую документацию и backlog.

При неполной реализации оставляйте верхнеуровневую задачу открытой и отмечайте готовые подэтапы отдельно.

# ChurchCMS architecture decisions

This is a concise decision log. Detailed ADR files can be introduced when decisions become more complex.

## D-001 — PHP 8.3 minimum

Accepted.

ChurchCMS targets PHP 8.3 or newer.

## D-002 — No mandatory external runtime dependencies

Accepted.

The CMS core must boot without Composer/vendor, frameworks or mandatory CDN/runtime services.

## D-003 — PostgreSQL primary, MySQL 8 compatibility where practical

Accepted.

PDO is the only database primitive used by application infrastructure.

## D-004 — Modular runtime inspired by Notes

Accepted.

ChurchCMS uses module manifests, registry and runtime providers. Notes is an architecture reference, not a codebase to copy wholesale.

## D-005 — Replace legacy VPDS runtime instead of incrementally modernizing it

Accepted.

Legacy code/database are migration/reference sources only.

## D-006 — Theme system is a first-class subsystem

Accepted.

Every site may use its own child/full theme. Business modules expose presentation contracts through logical template names.

## D-007 — Default theme modernizes legacy VPDS visual cues

Accepted.

Keep recognizable deep-blue/burgundy/architectural character while replacing fixed-width/table-era UI with responsive accessible design.

## D-008 — External systems use HTTP API, never direct DB access

Accepted.

Diocesan sites and other integrations consume versioned explicit API resources.

## D-009 — Publication syndication is explicit opt-in

Accepted.

Publishing on the local site does not automatically imply distribution to third-party aggregators.

## D-010 — External portal support uses adapters

Accepted.

Rambler, СМИ2, News Mail and future platforms must be implemented as independent adapters/renderers so portal-specific requirements do not pollute the core Publication model.

## D-011 — Specialized systems are integrated, not rewritten

Accepted.

Moodle remains LMS. OJS remains journal/publishing workflow. ChurchCMS provides public-site integration.

## D-012 — Multi-site compatibility should be preserved

Accepted.

Core/domain design should avoid assumptions that one process can only represent one website. Per-site theme and configuration are planned.


## D-013 — Web installer is the primary fresh-install experience

Accepted.

ChurchCMS must be installable without Composer or shell access. The installer should auto-detect everything it safely can, create/migrate the database, create the first administrator and then lock itself.

## D-014 — Administration is designed for non-technical operators

Accepted.

Routine editorial work should use plain language, sensible defaults, progressive disclosure and minimal steps. Technical concepts must not leak into normal editorial screens.

## D-015 — Comments are optional and moderated by default

Accepted.

Comments are a separate module attached to publications. They can be disabled globally/per-publication. Initial public submission is plain text and premoderated; external syndication never includes comments by default.


## D-016 — External channels are provider-agnostic and bidirectional

Accepted.

Social networks, messengers and video hosts use an open adapter contract. Provider IDs are strings rather than a database enum/whitelist. Adapters declare capabilities.

Outbound publication is explicit. Inbound content is stored in a review inbox and does not automatically overwrite or create official site publications.

## D-017 — The website is authoritative for official publications

Accepted.

External networks may contain arbitrary content that never exists on the official website. When a site publication is distributed outward, the site canonical URL remains its authoritative identity. External edits do not silently overwrite official content.

## D-018 — Public traffic is stateless and cache-first

Accepted.

Anonymous GET pages should be servable without PHP sessions and should be compatible with full-page/reverse-proxy/CDN caching. Heavy third-party integrations are prohibited from the request path.

## D-019 — SEO is a core public-content contract

Accepted.

Themes must render canonical/search/social metadata exposed by the content layer. Publications support automatic defaults plus optional editorial overrides. Sitemap and robots endpoints are generated by the SEO module.

## D-020 — Social share UI must not require third-party SDKs

Accepted.

Public share buttons use ordinary share URLs and the browser Web Share/Clipboard APIs from a local versioned script. Third-party tracking/widget JavaScript is not required.


## D-021 — Administration uses one shared Admin Shell

Accepted.

The existing dashboard/cards and individual admin templates are an implementation prototype, not the final administrative UX.

All administrative modules must render inside a shared Admin Shell with common navigation, site/user context, task notifications, consistent actions/states and responsive behavior. Modules may contribute navigation/actions through contracts, but may not create independent incompatible administration layouts.

The shell is optimized for non-technical parish and theological-school operators: domain language, minimal decisions per screen, progressive disclosure and obvious recovery paths take priority over exposing CMS internals.


## D-022 — Резервная копия предшествует изменению установленной системы

Принято.

ChurchCMS не должна изменять файлы установленной системы или применять новые миграции в рамках штатного обновления, пока не создана и не проверена резервная копия.

Копии по умолчанию хранятся вне публичного web-root. Базовый механизм не зависит от внешних `pg_dump`/`mysqldump`: логический снимок PostgreSQL/MySQL строится через PDO и сопровождается манифестом с SHA-256.

Первый инкремент покрывает создание и проверку снимка конфигурации, загрузок и данных БД. Восстановление, staging пакета обновления и автоматический откат реализуются отдельными безопасными инкрементами до закрытия пункта Update/backup workflow.

## D-024 — Пакет обновления проверяется во внешнем staging до применения

Принято.

Базовый формат обновления `churchcms-update-v1` является распакованным directory package с manifest, точным списком payload-файлов, размерами и SHA-256. Это позволяет проверять пакет без обязательной зависимости от ZIP/Composer или внешнего архиватора; транспортный архив может быть добавлен отдельно.

Staging располагается вне корня ChurchCMS. Source package также должен находиться вне корня приложения и не может быть вложен в staging. До завершения staging приложение не меняется.

Manifest обязан точно соответствовать установленной исходной версии, заявлять совместимый минимум PHP и перечислять весь payload. `config/local.php`, `storage`, `.git`, символические ссылки и небезопасные относительные пути в update package запрещены.

SHA-256 здесь является проверкой целостности, а не доказательством происхождения релиза. До автоматической сетевой загрузки обновлений необходимо отдельно определить доверенный источник или механизм аутентичности релизного пакета.

Применение staged package разрешается проектировать только как следующий инкремент после проверенной резервной копии и должно завершаться миграциями, healthcheck и автоматическим откатом при ошибке.


## D-025 — Автоматический apply сначала ограничен code-only пакетами

Принято.

До первого изменения установленной системы команда apply обязана повторно проверить staging-пакет, создать и проверить резервную копию, а затем иметь локальный файловый rollback для каждой замены, добавления и удаления.

Пакеты, добавляющие, изменяющие или удаляющие файлы миграций в `database/migrations/` или `modules/*/migrations/`, не применяются автоматически до появления проверенного механизма возврата старой схемы БД. Причина — текущий логический backup предназначен для данных и требует совпадения схемы; он не является DDL snapshot произвольной предыдущей версии.

Code-only apply обязан завершаться проверкой контрольных сумм, синтаксиса изменённых PHP-файлов, целевой версии и installation healthcheck. При ошибке файловые операции откатываются в обратном порядке.

Это ограничение не отменяет будущую поддержку миграций; оно запрещает заявлять безопасный rollback раньше, чем он реально реализован и протестирован.


## D-026 — Оператор не вводит серверные пути для backup/update

Принято.

Повседневные операции резервного копирования и обновления выполняются через общий Admin Shell. Каталоги backup/staging задаются конфигурацией установки и не выводятся как редактируемые поля обычному оператору.

Раздел «Система» может создавать и повторно проверять резервные копии, показывать installation healthcheck и готовые staging-пакеты, а также запускать подтверждённый code-only apply. Все изменяющие действия защищаются RBAC + CSRF и записываются в audit log.

Повреждённый, устаревший или schema-changing staging-пакет не получает кнопку применения. Восстановление из Admin Shell разрешено только через единый оркестратор БД + config/uploads с отдельным аварийным снимком текущего состояния.


## D-027 — Production-ошибки не раскрывают внутренности приложения

Принято.

Главный web front controller регистрирует error handler до bootstrap ядра.

При необработанном исключении или критической ошибке production-ответ не должен содержать класс исключения, внутренний message, абсолютный путь файла или stack trace. Клиент получает нейтральную ошибку и request ID; подробность остаётся в приватном server/application log.

`app.debug` по умолчанию выключен и может явно включаться только для локальной диагностики.

API/health запросы получают машиночитаемый JSON 500, браузерные страницы — минимальный HTML 500. Error responses не кешируются.


## D-028 — Смена пароля отзывает старые административные сессии через auth_version

Принято.

У каждого администратора хранится монотонная `auth_version`. При успешном входе её текущее значение записывается в сессию, а каждый защищённый admin-запрос сравнивает значение с БД.

При смене пароля `auth_version` увеличивается. Текущая сессия получает новое значение, новый session ID и новый CSRF token; все другие сессии остаются со старой версией и перестают считаться аутентифицированными.

Такой механизм не требует обязательного централизованного session-store и позволяет отзывать старые сессии сразу после ротации пароля.

Forgotten-password/reset flow остаётся отдельной задачей и не должен использовать пароль или reset token в логах как канал доставки.


## D-029 — Каждая установка ChurchCMS автономна и может участвовать в федерации

Принято.

Одна установка ChurchCMS может представлять приход, собор, монастырь, благочиние, епархию, митрополию, духовную школу или иную церковную организацию.

Установка имеет постоянный публичный `instance_id` и корневую organization unit. Профиль установки задаёт стартовые рекомендации, но не ограничивает доступные модули.

Церковная иерархия и техническая федерация являются разными сущностями. Локальный `parent_id` описывает организационную структуру, а federation link — доверенную связь с другой независимой установкой.

Связь может быть `parent`, `child` или `peer`. Она необязательна: узел должен продолжать полноценную работу при отсутствии сети, вышестоящего ChurchCMS или после отключения federation link.

Факт организационного подчинения не выдаёт удалённой стороне административных прав. Обмен ограничивается явными inbound/outbound scopes. Future remote write/delegated administration, если будет нужен, проектируется отдельным opt-in контрактом.

Общая БД между независимыми ChurchCMS не используется. Межсайтовый обмен строится поверх versioned HTTP API, stable public IDs и canonical ownership.


## D-030 — Организационная структура архивируется вместо hard-delete

Принято.

Организационные единицы являются стабильными владельцами/контекстами будущих людей, документов, публикаций, событий и федеративных связей. Поэтому обычный Admin UI не удаляет строки `organization_units` физически.

Операция «В архив» переводит выбранный узел и всё его поддерево в статус `archived`. Восстановление также применяется к поддереву. Корневую организацию `site_key` архивировать нельзя.

Изменение родителя или slug пересчитывает canonical path всего поддерева в одной транзакции. Перемещение внутрь собственного потомка и создание второго независимого root для того же `site_key` запрещены.

Ограничение редактора конкретной епархией/благочинием реализуется через `admin_role_scopes`; правила наследования зафиксированы отдельным решением D-031.


## D-031 — Organization scope наследуется только вниз по локальному дереву

Принято.

Scope назначения роли хранится в существующем `admin_role_scopes` как `site_key + scope_type + scope_key`. Для церковной структуры используется `scope_type = organization`, а `scope_key` содержит стабильный public ID корневой организации области доступа.

Назначение роли без scope-записей остаётся глобальным. Если у назначения роли есть scope-записи, оно не должно незаметно превращаться в глобальное право.

Organization scope включает сам корневой узел области и его локальных потомков по canonical path. Право не наследуется вверх к родителю и не распространяется на соседние ветки.

Проверка области выполняется централизованно через `AuthorizationService` и `OrganizationAccessService`. Контроллеры не должны самостоятельно воспроизводить SQL или собственные варианты проверки дерева.

Суперадминистратор остаётся глобальным исключением. Федеративная связь с другим ChurchCMS не расширяет локальный RBAC и сама по себе не выдаёт административных прав.


## D-032 — Federation pairing повторно проверяет remote identity и защищает discovery от SSRF

Принято.

Discovery не создаёт доверие само по себе. Admin Shell сначала показывает оператору публичную identity удалённого ChurchCMS, а перед сохранением federation link повторно получает metadata с удалённого узла. Значения remote instance/organization ID из HTML-формы не являются источником истины.

Pairing и revoke требуют право `settings.manage` и CSRF-защиту. Federation link не расширяет локальный RBAC и не выдаёт удалённому узлу административных прав.

Публичный discovery выполняется только по HTTPS. Частные и loopback-адреса запрещены по умолчанию и разрешаются только явной локальной настройкой `federation.allow_private_discovery=true`, необходимой для закрытых сетей. Link-local, служебные/зарезервированные адреса и смешанные public/private DNS-ответы отклоняются.

Credential не участвует в первом discovery-запросе, вводится только на шаге подтверждения и хранится зашифрованно через `SecretVault`. Автоматический reciprocal token exchange пока не объявляется реализованным: credential может быть передан оператору по отдельному доверенному каналу.

Revoke не удаляет federation link физически. Связь получает статус `revoked`, encrypted credential и sync cursor очищаются. Повторное pairing того же remote instance переиспользует сохранённую запись, что сохраняет стабильный public ID и историю аудита.

## D-033 — Карточка человека и назначения имеют разные организационные связи

Принято.

Карточка человека имеет одного канонического локального владельца — `owner_organization_public_id`. Это организация текущего `site_key`, которая отвечает за редактирование и локальную идентичность записи.

Служение, должность или иное назначение не выводится из владельца карточки. Каждая запись `person_appointments` отдельно связывает человека с конкретной organization unit, названием должности, типом и периодом. Поэтому один человек может одновременно иметь несколько назначений в разных подразделениях одного сайта.

Новые карточки без явно выбранного владельца получают корневую организацию сайта. Если корневой организации нет, создание отклоняется: для нового модуля не вводится legacy-состояние с неопределённым owner.

И сервисный слой, и составные внешние ключи `(site_key, public_id)` запрещают связывать человека или назначение с организацией другого сайта. Федеративные remote projections в эту локальную модель автоматически не записываются и должны проектироваться отдельным контрактом синхронизации.

## D-034 — Health-проверка federation link не меняет доверие молча

Принято.

Оператор с правом `settings.manage` может повторно проверить неотозванную federation-связь через тот же защищённый discovery-клиент, который используется при pairing. Сохранённый outbound credential в health-запрос не передаётся.

Успешный discovery считается подтверждением связи только тогда, когда одновременно совпадают ранее сохранённые `remote_instance_id` и `remote_organization_public_id`. В этом случае статус становится `active`, обновляются `last_seen_at` и безопасные публичные metadata удалённого узла, а прежняя ошибка очищается.

Если по сохранённому адресу отвечает другая постоянная identity, связь получает статус `conflict`. Новые instance/root ID не записываются поверх доверенной identity, credential и scopes не меняются. Оператор должен отдельно разобраться с причиной смены узла или выполнить явный revoke/pairing.

Сетевая или протокольная ошибка переводит связь в `error`, сохраняя последний успешный `last_seen_at`. Повторная проверка является штатным retry и может вернуть связь в `active`.

Health-проверка не изменяет inbound/outbound scopes, encrypted credential и sync cursor. Результат фиксируется в audit log; сырые исключения остаются в серверном журнале и не показываются как операторская диагностика.

## D-035 — Tombstone публикации хранится отдельно от текущего состояния материала

Принято.

Partner API не должен заставлять агрегатор угадывать удаление по исчезновению
материала из списка. При снятии ранее опубликованной публикации с target
`diocese` ChurchCMS сохраняет отдельный tombstone со stable public ID
публикации, `organization_owner_id`, причиной и UTC-временем удаления.

Смена статуса публикации и запись tombstone выполняются в одной транзакции.
Если tombstone сохранить не удалось, withdraw также откатывается: источник не
должен считать материал снятым, пока не может сформировать надёжный сигнал для
partner sync.

Tombstone не содержит body, редакционные поля, внутренние DB ID или секреты.
Повторный withdraw обновлять или размножать событие не должен. Материалы без
partner target `diocese` tombstone в этот поток не создают.

Tombstone хранится отдельно от основной строки публикации. Повторная публикация
может создать более новое состояние материала, но не стирает исторический факт
предыдущего удаления. Принимающая сторона обязана разрешать конкурирующие
upsert/delete по времени изменения. Хранилище remote projections реализовано
решением D-036, а безопасный поток синхронизации Publications — решением D-038.

## D-036 — Remote projection не становится локальной канонической сущностью

Принято.

Данные, полученные через federation sync, хранятся отдельно от локальных Publications, Pages и других канонических сущностей. Ключ remote projection состоит из federation link, типа объекта и stable public ID источника. Это сохраняет происхождение данных и не позволяет удалённому узлу неявно получить локальное владение записью.

Применение upsert и tombstone разрешено только для активной доверенной federation-связи. События сравниваются по удалённому времени изменения: более старое событие игнорируется, tombstone с тем же временем имеет приоритет над active-состоянием, а только более новый upsert может восстановить удалённую projection.

Tombstone разрешено сохранить даже без ранее полученного полного объекта. Это необходимо для корректной частичной или возобновлённой синхронизации, когда событие удаления пришло раньше локального full sync.

Отзыв federation link немедленно запрещает дальнейшее применение remote projection через сервисный слой. Фоновая синхронизация Publications реализована отдельным решением D-038; обобщение на остальные типы данных и агрегированные ленты остаются следующими инкрементами.

## D-037 — Восстановление из Admin Shell всегда создаёт аварийный снимок текущего состояния

Принято.

Восстановление резервной копии из Admin Shell является одной подтверждаемой операцией для БД, `config/local.php` и `storage/uploads`. До первого изменения ChurchCMS повторно проверяет выбранную копию и создаёт отдельную проверенную аварийную копию текущего состояния.

Если после начала восстановления возникает ошибка, оркестратор пытается вернуть из аварийной копии сначала БД, затем файловую часть и повторно проверяет installation healthcheck. Если автоматический возврат также завершается ошибкой, операция не объявляется успешной: оператор получает нейтральное сообщение, а серверный журнал фиксирует необходимость ручной проверки.

Восстановление из Admin Shell предназначено для возврата состояния той же установки, а не для миграции между окружениями. До изменения данных конфигурация копии должна указывать на то же подключение к БД и тот же каталог резервных копий, что и текущая установка. Копия с другой инфраструктурной конфигурацией из Admin Shell отклоняется до любых изменений.

Это решение не является rollback схемы для произвольного schema-changing update: логический backup по-прежнему требует совпадения текущей схемы с копией. Миграционный rollback остаётся отдельной задачей.

## D-038 — Курсор federation sync продвигается только после применения страницы

Принято.

Для публикаций и tombstone используются независимые составные курсоры `updated_at + public_id`. Одного времени недостаточно: несколько записей могут иметь одинаковый `updated_at`, поэтому partner API сортирует поток по времени и стабильному public ID и возвращает обе части следующего курсора.

Фоновый обработчик сохраняет курсор публикаций только после успешного применения всей полученной страницы. Затем отдельно обрабатывает tombstone-поток. Если второй запрос или применение tombstone завершается ошибкой, подтверждённый курсор публикаций сохраняется, а курсор tombstone остаётся прежним. Повторный запуск продолжает именно незавершённый поток; повторное применение уже полученных событий безопасно благодаря правилам remote projections из D-036.

Ошибка синхронизации не меняет состояние доверия federation link. Discovery-health и sync-state разделены: `status/last_seen_at/last_error` описывают identity и доступность доверенной связи, а `last_sync_at/last_sync_error` — последний проход обмена данными.

Один запуск `bin/federation-sync.php` ограничен числом связей и размером страницы и не содержит бесконечного цикла. Планировщик или cron запускает следующие проходы отдельно. Это позволяет управлять временем выполнения и безопасно повторять работу после сбоя.

Запись курсора выполняется с проверкой ожидаемого предыдущего значения. Если другой процесс уже продвинул ту же связь, устаревший запуск не может записать свой курсор поверх нового состояния и не должен затирать успешное sync-состояние ложной ошибкой.

Текущий инкремент синхронизирует Publications. Остальные типы remote projections и агрегированные ленты должны подключаться к тому же принципу курсоров отдельными следующими инкрементами.

## D-039 — Релизный пакет принимается только с подписью закреплённого ключа

Принято.

SHA-256 отдельных файлов подтверждает целостность относительно манифеста, но не подтверждает происхождение самого манифеста. Поэтому ChurchCMS не считает пакет обновления доверенным без цифровой подписи всех полей `manifest.json`, кроме объекта `signature`.

Манифест содержит `signature.algorithm = openssl-sha256`, `signature.key_id` и Base64-подпись. Для проверки используется публичный ключ из `operations.update_trusted_public_keys[key_id]`. При отсутствии подписи, неизвестном `key_id`, повреждённой подписи или неверном публичном ключе пакет отклоняется до копирования в staging.

Подписываемое представление манифеста формируется детерминированно: ключи JSON-объектов сортируются, порядок списков сохраняется, объект `signature` исключается. Подпись тем самым покрывает версии, минимальную версию PHP, полный список файлов, размеры, SHA-256 и удаления.

Проверка выполняется не только при первичном staging, но и при каждом `inspect`. `UpdatePackageApplier` начинает работу с `inspect`, поэтому подмена уже staged-манифеста блокируется до backup и до изменения установленного приложения.

Установленный ChurchCMS хранит только публичные ключи. Приватный релизный ключ остаётся вне репозитория и вне production-установок; штатный `tools/update-sign.php` требует его по абсолютному пути и отказывается использовать ключ внутри репозитория. Для зашифрованного PEM пароль передаётся через `CHURCHCMS_UPDATE_SIGNING_PASSPHRASE`, а не через аргумент командной строки.

Ротация выполняется добавлением нового `key_id` параллельно со старым, выпуском релиза новым ключом и последующим удалением старого public key после переходного периода. Удаление скомпрометированного `key_id` автоматически делает ранее staged-пакеты с этим ключом неприменимыми при следующем `inspect`.

Цифровая подпись не заменяет безопасную сетевую доставку. Автоматическое получение релиза из удалённого источника остаётся отдельным инкрементом и обязано использовать эту проверку как обязательный барьер перед staging.


## D-040 — Сетевой источник обновлений задаётся локально и не управляется браузером

Принято.

ChurchCMS не принимает URL релиза из Admin Shell. Точный HTTPS URL подписанного `manifest.json` задаётся в локальной конфигурации как `operations.update_release_manifest_url`. Это уменьшает SSRF-поверхность и отделяет административное действие «получить релиз» от доверия к самому адресу источника.

Перед загрузкой payload ChurchCMS получает только манифест и проверяет его цифровую подпись по закреплённому публичному ключу. Только после успешной подписи разрешено скачать перечисленные файлы. Файлы строятся относительно каталога манифеста, поэтому удалённый пакет не может указать второй origin.

Сетевой клиент допускает только HTTPS, запрещает redirects, URL credentials, query и fragment. DNS-ответы проверяются до запроса: частные, loopback, link-local и зарезервированные адреса запрещены, а проверенный публичный адрес закрепляется через cURL. Для этой операции cURL является осознанным дополнительным требованием безопасности; небезопасный fallback через обычное повторное DNS-разрешение не используется.

Размер манифеста, отдельного файла и всего пакета ограничен. Каждый payload-файл после загрузки обязан совпасть с подписанным размером и SHA-256. Временная загрузка не является staging: только полностью проверенный локальный каталог передаётся существующему `UpdatePackageStager`, который повторяет проверки подписи, путей и контрольных сумм.

Получение пакета и его применение остаются разными действиями. Сетевая загрузка не меняет файлы работающего ChurchCMS, не запускает миграции и не создаёт иллюзию безопасного rollback схемы БД. Schema-changing apply остаётся заблокированным до отдельного решения.

# Проверка релизного кандидата ChurchCMS 1.0

Этот документ описывает обязательный технический проход перед созданием релиза 1.0. Актуальный состав версии и границы релиза зафиксированы в `docs/RELEASE_1.0.md`.

Функциональный состав 1.0 реализован. До финального тега `1.0.0` остаётся внешний по отношению к GitHub Actions этап: эталонный performance gate на зафиксированном production-подобном сервере.

## Что проверяет автоматический RC gate

Workflow `.github/workflows/release-candidate-gate.yml` заново проверяет текущий commit и не опирается на старые зелёные запуски.

Обязательные контуры:

1. **Предрелизный аудит**
   - PHP 8.3+;
   - обязательные расширения;
   - синтаксис PHP;
   - валидность миграций;
   - целостность тем и шаблонов.

2. **Чистая установка на PostgreSQL**
   - настоящий `install.php` запускается через HTTP;
   - проверяется CSRF мастера установки;
   - создаются схема и корневая организация;
   - создаётся первый администратор;
   - проверяется роль `superadmin`;
   - после установки installer должен отвечать `404` и больше не выполнять установку.

3. **Readiness и безопасность административного доступа**
   - `InstallationHealthCheck` обязан вернуть `ready=true`;
   - выполняется smoke восстановления пароля администратора.

4. **Резервная копия и восстановление**
   - создаётся и проверяется backup;
   - после снимка изменяются данные БД, `config/local.php` и файл в `storage/uploads`;
   - выполняется `restore-db`;
   - выполняется `restore-files`;
   - проверяется возврат данных, конфигурации и uploads к состоянию снимка.

5. **Подписанное code-only обновление**
   - генерируется отдельная тестовая пара ключей;
   - пакет подписывается штатным `tools/update-sign.php`;
   - пакет проходит staging;
   - updater обязан создать backup перед применением;
   - после применения проверяются версия и PHP-синтаксис нового файла.

6. **Schema-changing обновление**
   - пакет содержит новую `ReversibleMigration`;
   - миграция применяется штатным updater;
   - проверяется новая таблица и запись миграции.

7. **Rollback после ошибки уже после миграции**
   - следующий пакет содержит обратимую миграцию и намеренно повреждённый PHP-файл;
   - применение обязано завершиться ошибкой;
   - версия должна вернуться к предыдущей;
   - повреждённый файл и миграция не должны остаться в установке;
   - добавленная таблица должна быть удалена;
   - запись неуспешной миграции не должна остаться в `churchcms_migrations`.

8. **MySQL 8.4**
   - применяется полный набор миграций;
   - повторный запуск мигратора обязан быть идемпотентным;
   - список применённых миграций сверяется с репозиторием;
   - `InstallationHealthCheck` обязан вернуть `ready=true`.

Итоговый job `RC 1.0 — итог` становится зелёным только если все обязательные контуры завершились успешно.

## Production-профиль

Релизный кандидат дополнительно опирается на уже проверенный production-пакет:

- `deploy/nginx/churchcms.conf.example` — HTTPS, ACME, закрытие внутренних путей и единый front controller;
- `deploy/php-fpm/churchcms.conf.example` — отдельный PHP-FPM 8.3 pool;
- `deploy/cron/churchcms.example` — фоновые задачи с `flock`;
- `docs/DEPLOYMENT.md` — установка, права, БД, TLS, cron, backup/update и post-deploy checklist.

Перед тегом выбранный production-подобный сервер должен быть развёрнут по этому профилю и пройти post-deploy проверки.

## Как запустить

RC gate автоматически запускается при изменениях критичных для установки, миграций, backup/restore и updater. Перед релизом его также нужно запустить вручную через GitHub Actions на commit, из которого будет собираться версия 1.0.

Локальный базовый аудит:

```bash
php bin/release-audit.php
```

Он полезен перед отправкой изменений, но не заменяет RC workflow с реальными PostgreSQL/MySQL.

## Первый стабильный релиз и обновления

Для первого стабильного релиза нельзя придумывать искусственную «предыдущую поддерживаемую версию» только ради проверки upgrade path. Чистая установка, updater-механика, code-only update и schema-changing rollback уже проверяются RC gate.

Проверка обновления с предыдущей версии становится обязательной, когда такая поддерживаемая версия действительно существует.

## Последний обязательный gate — производительность

GitHub Actions не считается эталонным сервером производительности.

Перед финальным тегом `1.0.0` нужно:

1. выбрать и зафиксировать эталонный Nginx + PHP-FPM стенд;
2. зафиксировать CPU, RAM, тип хранилища, PHP и СУБД;
3. развернуть релизный commit;
4. подготовить репрезентативный набор данных;
5. выполнить `tools/performance/http-load.php`;
6. сохранить реальные p50/p95/p99, RPS и долю ошибок;
7. утвердить `thresholds.json`;
8. выполнить:

```bash
php bin/release-audit.php \
  --performance-result=/path/http-load.json \
  --performance-thresholds=/path/thresholds.json
```

Только после зелёного RC workflow и зелёного performance release-gate commit может быть помечен тегом `1.0.0`.

## Внешние задачи, которые не блокируют 1.0

- legacy VPDS migration — до получения подтверждённого формата legacy-экспорта;
- Rutube outbound upload — до появления подтверждённого официального upload API;
- СМИ2 — до получения актуальной партнёрской спецификации;
- News Mail — до получения onboarding-контракта;
- пилотные внедрения и сбор редакторской обратной связи.

Эти пункты остаются в roadmap/backlog, но не должны маскироваться под незавершённость технического ядра 1.0.

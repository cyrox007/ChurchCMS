# Наблюдаемость и обслуживание журналов

ChurchCMS пишет необработанные ошибки приложения в `storage/logs/error.log`. Каждая запись содержит время UTC, `request_id`, класс исключения, сообщение, файл, строку и ограниченный стек вызовов. `request_id` также возвращается клиенту в заголовке `X-Request-ID`, поэтому обращение пользователя можно сопоставить с записью сервера без раскрытия внутренней ошибки в production.

## Автоматическая ротация

После загрузки ядра `ErrorHandler` использует `LogManager`. Перед очередной записью он проверяет размер `error.log`. Если новая запись превысит лимит, текущий файл атомарно переименовывается в архив вида:

```text
error.log.20261013-041500-1234-a1b2c3
```

По умолчанию применяются следующие ограничения:

- максимальный размер активного журнала — 10 МиБ;
- максимум 10 архивов;
- максимальный возраст архива — 30 дней.

Эти значения можно переопределить в `config/local.php`:

```php
'operations' => [
    'logs' => [
        'max_bytes' => 20 * 1024 * 1024,
        'max_archives' => 14,
        'max_age_days' => 45,
    ],
],
```

Ротация выполняется под файловой блокировкой. Каталог журналов и сам `error.log` не должны быть символическими ссылками. Архивы получают права `0640`. Если ядро ещё не успело загрузить автозагрузчик, ранний аварийный обработчик сохраняет прежний безопасный fallback-записи без попытки вызвать менеджер ротации.

## Ручное обслуживание и cron

Команда не требует подключения к БД и может работать во время частичной аварии приложения:

```bash
php bin/log-maintenance.php
```

Принудительная ротация:

```bash
php bin/log-maintenance.php --rotate
```

Разовые лимиты для команды:

```bash
php bin/log-maintenance.php \
  --max-bytes=10485760 \
  --max-archives=10 \
  --max-age-days=30
```

Для обычного сервера достаточно запускать обслуживание раз в сутки, например через cron:

```cron
17 3 * * * cd /var/www/churchcms && /usr/bin/php bin/log-maintenance.php >> /var/log/churchcms-log-maintenance.log 2>&1
```

Автоматическая ротация по размеру происходит и без cron; периодический запуск нужен прежде всего для гарантированной очистки старых архивов в периоды, когда приложение почти не получает запросов.

## Диагностика

При расследовании ошибки сначала запросите у пользователя код обращения (`request_id`), затем найдите его в активном журнале и архивах. Не публикуйте содержимое журналов в web-root и не выдавайте их через публичный HTTP-маршрут.

Проверка реализации выполняется `tools/log-maintenance-smoke.php`: она покрывает ротацию по размеру, принудительную ротацию, ограничение количества архивов, удаление устаревших файлов и защиту от символической ссылки.

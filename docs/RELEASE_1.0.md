# ChurchCMS 1.0 — состояние релиза

## Текущий статус

ChurchCMS 1.0 **ещё не готов к живому развёртыванию**.

Ранее релизный контур был преждевременно признан функционально завершённым. Для версии 1.0 действует исходный принцип: перед первым живым тестированием должны быть закрыты все задуманные для 1.0 функции, проверен современный интерактивный UX административной части и пройдены технические релизные проверки.

Ветка `release/1.0.0-rc1` считается промежуточным снимком и не является финальной заморозкой версии.

## Что обязательно входит в 1.0

### Базовая платформа

- PHP 8.3+ standalone runtime без обязательного Composer/vendor runtime;
- PostgreSQL и MySQL;
- web-installer и installation healthcheck;
- Admin Shell, RBAC, organization scopes, CSRF/session/security headers;
- audit log и production error handling;
- backup/restore;
- подписанные обновления с code-only и schema-changing rollback;
- production-профиль Nginx + отдельный PHP-FPM pool + cron-workers;
- ротация журналов.

### Контент и приходской профиль

- публикации, страницы, меню, поиск;
- Media, галереи и документы;
- духовенство и назначения;
- богослужения и события;
- SEO, sitemap, redirects, revisions;
- модерируемые комментарии.

### Экономичное долговременное Media-хранилище

Для многолетних новостных архивов в 1.0 входит отдельный эксплуатационный контур Media:

- точная дедупликация blob по SHA-256;
- автоматическая WebP-веб-версия тяжёлых JPEG/PNG/WebP без изменения оригинала;
- пакетная оптимизация существующего фотоархива;
- S3-compatible архив старых оригиналов;
- обязательная проверка размера и SHA-256 до разрешения удаления локальной копии;
- автоматическое восстановление архивного blob в локальный cache при обращении по прежнему публичному URL;
- dry-run всех освобождающих место операций;
- отчёт local/logical/derivatives/archive, orphan/missing и прогноз заполнения диска;
- небольшие лимитированные партии обслуживания вместо тяжёлого монолитного процесса.

Подробный эксплуатационный контракт: `docs/MEDIA_STORAGE.md`.

### Соборный профиль

- служения/отделы;
- святыни;
- святые;
- воскресная школа;
- библиотека;
- donation/prayer-request integration boundaries;
- агрегируемые потоки главной страницы.

### Образовательный профиль

- образовательные программы;
- кафедры и преподаватели;
- приёмная кампания;
- обязательные сведения;
- расписания;
- научная деятельность;
- Moodle/OJS adapters.

### Федерация и внешнее распространение

- organization tree и federation links;
- pairing, scopes, remote projections, tombstones и health dashboard;
- Telegram, VK, MAX, YouTube;
- Rutube inbound и полный внутренний outbound-контур с обязательной внешней приёмкой официального upload-доступа;
- RSS/Rambler syndication;
- СМИ2 и News Mail как отдельные адаптеры/целевые профили распространения;
- журнал экспортов, target-specific overrides и валидаторы;
- подписанные distribution webhooks с retry/dead-letter.

### Legacy migration

Для 1.0 реализован полный каркас миграции VPDS:

- mapping legacy schema;
- перенос контента;
- перенос Media с проверками контрольных сумм;
- перенос URL/redirect;
- стратегия пользователей;
- диагностика битых ссылок/медиа;
- dry-run и отчёт миграции.

Если конкретный legacy-экспорт отличается от ожидаемого формата, импортёр останавливается с диагностикой, а не требует ручного изменения кода.

### Современный интерактивный UX

Обязательное правило 1.0: операции внутри уже открытой административной страницы выполняются без полной перезагрузки, если переход на другую страницу не является целью действия.

К этому относятся:

- сохранение и удаление;
- publish/unpublish/withdraw/cancel и другие переключатели состояний;
- модерация;
- массовые операции;
- загрузка файлов;
- retry/requeue/sync/test connection;
- изменение порядка;
- фильтры и локальная пагинация там, где пользователь остаётся в том же рабочем контексте;
- действия в модальных/встроенных формах.

Для каждой такой операции обязательны информативные состояния:

- выполнение;
- успех;
- ошибка;
- пустой результат, если применимо;
- защита от повторной отправки.

Базовый контракт описан в `docs/UX_ASYNC_RELEASE_GATE.md`. Автоматический Chromium-проход проверяет POST + redirect, multipart, двойную отправку, фильтры, пагинацию, Back/Forward, серверную ошибку и допустимые обычные переходы. Во время первого запуска этого gate была обнаружена и исправлена потеря полей `FormData` после преждевременной блокировки формы.

## Внешние контракты

Отсутствие открытой публичной документации партнёра не является основанием автоматически переносить задачу после 1.0.

Перед релизом необходимо:

1. реализовать всю часть адаптера, не зависящую от закрытых учётных данных;
2. зафиксировать официальный onboarding/контакт партнёра;
3. добавить проверяемую конфигурацию и диагностику готовности;
4. явно отделить «код не реализован» от «проверка требует партнёрского доступа»;
5. до финального тега выполнить сквозную внешнюю приёмку там, где она входит в исходный scope 1.0.

Для Rutube внутренний outbound-контур ChurchCMS реализован: `publish.video`, Media preflight, очередь, dead-letter, классификация постоянных ошибок, диагностический статус и заменяемый `RutubeUploadTransport`. Скрытые endpoint Rutube Studio не используются. Официально опубликованный машинный upload API на момент проверки не найден, поэтому обязательным внешним блокером 1.0 остаётся получение подтверждённого партнёрского upload-контракта и сквозной тест реальной загрузки. Подробности: `docs/RUTUBE_OUTBOUND.md`.

Для Новости Mail внутренний целевой feed/profile, validator и административная диагностика реализованы. Внешним блокером остаётся партнёрский onboarding и сквозная приёмка после получения подтверждённого контракта.

Для СМИ2 внутренний целевой профиль распространения, полнотекстовая RSS-лента, validator и административная диагностика реализованы. Внешним блокером остаётся партнёрский onboarding и подтверждение канала со стороны площадки.

## Порядок завершения версии

1. Закрыть оставшиеся внешние обязательные приёмки и подтвердить, что кодовый функциональный scope 1.0 больше не имеет незавершённых внутренних контуров.
2. Поддерживать AJAX/UX browser gate зелёным для всех административных действий.
3. Прогнать автоматические smoke/RC проверки.
4. Выполнить эталонный performance gate.
5. Только после этого развернуть систему вживую и пройти ручные сценарии, включая внешний Media archive.
6. Исправить найденные дефекты и повторить RC/performance проверки, если изменения затрагивают критичные контуры.
7. Создать новую финальную release branch/RC.
8. Создать тег `1.0.0`.

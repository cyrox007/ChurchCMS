# Media Storage & Optimization

ChurchCMS рассчитан на сайты, которые годами накапливают фотографии, аудио, видео и документы. Исторические материалы не должны исчезать только потому, что локальный диск VPS закончился.

Основной принцип: **логическая Media-запись и публичный URL живут независимо от физического места хранения blob**.

## Что уже экономит место

`MediaBlobStorage` хранит blob по SHA-256. Повторная загрузка полностью одинакового файла не создаёт вторую физическую копию. В панели медиатеки это отражается как экономия дедупликацией.

Для JPEG, PNG и WebP ChurchCMS создаёт производную веб-версию `web`:

- формат WebP;
- максимальная сторона по умолчанию — 2560 px;
- качество по умолчанию — 82;
- EXIF/GPS исходника в веб-копию не переносятся;
- исходный файл не изменяется;
- публичные галереи предпочитают веб-версию исходному тяжёлому изображению.

Существующий архив изображений можно обработать малыми партиями:

```bash
php bin/media-storage.php --action=optimize-images --limit=100
php bin/media-storage.php --action=optimize-images --limit=100 --apply
```

Первая команда — только dry-run. Изменения выполняются лишь с `--apply`.

## Внешний архив

Поддерживается S3-compatible HTTPS-хранилище. Это может быть облачный S3-провайдер или совместимое объектное хранилище, которым управляет оператор.

Настройка выполняется только в `config/local.php`:

```php
'media' => [
    'archive' => [
        'driver' => 's3',
        'endpoint' => 'https://s3.example.org',
        'bucket' => 'churchcms-media',
        'region' => 'us-east-1',
        'access_key' => '...',
        'secret_key' => '...',
        'prefix' => 'churchcms-media',
        'archive_after_days' => 90,
        'local_cache_days' => 30,
    ],
],
```

Учётные данные не сохраняются в БД и не выводятся в Admin Shell.

Endpoint считается доверенной операторской конфигурацией. Это позволяет использовать в том числе приватный MinIO/NAS. Значение не должно формироваться из пользовательского ввода.

## Безопасность переноса

ChurchCMS никогда не удаляет локальный blob сразу после HTTP `PUT`.

Перед разрешением удаления выполняется последовательность:

1. загрузка объекта;
2. `HEAD` и сверка размера;
3. сверка сохранённого SHA-256 metadata;
4. полная обратная загрузка во временный файл;
5. повторная проверка размера и SHA-256;
6. фиксация состояния `ready` в `media_archive_locations`;
7. только после этого локальная копия может быть удалена.

Если любая проверка не проходит, локальный оригинал остаётся на месте.

## Архивирование старых оригиналов

Посмотреть кандидатов старше 90 дней:

```bash
php bin/media-storage.php --action=archive --older-than=90 --limit=100
```

Архивировать, сохранив локальные копии:

```bash
php bin/media-storage.php --action=archive --older-than=90 --limit=100 --apply
```

Архивировать и после подтверждённой проверки освободить локальный диск:

```bash
php bin/media-storage.php --action=archive --older-than=90 --limit=100 --delete-local --apply
```

Обработка идёт ограниченными партиями, поэтому её можно безопасно запускать на слабых VPS.

## Доступность старых фотографий

Публичный URL Media не меняется после архивирования.

Если нужного blob уже нет локально, `MediaPublicFileService`:

1. находит подтверждённую архивную запись;
2. скачивает объект во временный файл;
3. проверяет размер и SHA-256;
4. возвращает blob в локальный content-addressed cache;
5. отдаёт файл по прежнему URL.

Таким образом, старая фотография остаётся доступна спустя годы после удаления локальной архивной копии.

Текущий backend рассчитан на online/nearline object storage с быстрым чтением. Классы deep cold storage, где восстановление занимает минуты или часы, **нельзя** подключать к этому синхронному пути без отдельной асинхронной очереди восстановления.

## Очистка локального кэша

ChurchCMS удаляет локальный cache только для blob, у которых уже есть подтверждённое состояние `ready` во внешнем архиве.

Dry-run:

```bash
php bin/media-storage.php --action=prune-cache --older-than=30 --limit=500
```

Применение:

```bash
php bin/media-storage.php --action=prune-cache --older-than=30 --limit=500 --apply
```

Логические Media-записи, ссылки публикаций, галереи и архивные объекты при этом не удаляются.

## Отчёт и прогноз заполнения

```bash
php bin/media-storage.php --action=report
```

Отчёт включает:

- логический объём Media;
- объём уникальных SHA-blob;
- размер производных файлов;
- фактическое локальное место;
- экономию дедупликацией;
- осиротевшие `.blob`;
- ссылки на отсутствующие blob;
- количество объектов, доступных только через архив;
- объём подтверждённого архива;
- свободное место файловой системы.

Для прогноза роста периодически сохраняйте снимок:

```bash
php bin/media-storage.php --action=report --record-snapshot
```

После появления снимков за разные дни ChurchCMS оценивает средний рост локального Media и примерное число дней до заполнения диска.

## Осиротевшие и отсутствующие файлы

Отчёт различает:

- `orphan` — физический `.blob` существует, но больше не связан ни с одной Media/derivative записью;
- `missing` — запись ссылается на blob, которого нет ни локально, ни в подтверждённом архиве;
- `archived_only` — локальной копии нет, но архивная копия подтверждена и может быть восстановлена.

Автоматическое удаление orphan-файлов намеренно не включено в первую версию. Сначала оператор должен увидеть отчёт и убедиться, что причина понятна.

## Резервное копирование

Архивное объектное хранилище — отдельный слой данных. Обычный backup БД ChurchCMS сохраняет ссылки и состояние архива, но не копирует сами объекты S3.

Для production рекомендуется включить у провайдера:

- versioning или аналогичную защиту;
- replication/offsite backup при необходимости;
- правила retention;
- отдельный мониторинг доступности bucket.

Не следует ежедневно включать многолетний Media-архив в полный локальный backup VPS: это уничтожает экономию диска.

## Ограничения первого этапа

В текущем этапе реализованы:

- точная SHA-256 дедупликация;
- WebP веб-версии изображений;
- пакетная оптимизация старых изображений;
- S3-compatible архив;
- проверенный перенос и восстановление;
- локальный cache;
- dry-run;
- аудит диска, orphan/missing и прогноз роста.

Аудио- и видеотранскодирование не выполняется скрыто внутри PHP. Для него требуется отдельный безопасный worker с FFmpeg и лимитами ресурсов; этот слой следует подключать поверх уже реализованного `media.storage` контракта.

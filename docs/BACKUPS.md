# Резервное копирование и обновления

Этот документ описывает текущий фундамент резервного копирования ChurchCMS. Полный мастер обновления ещё не завершён.

## Где хранятся копии

По умолчанию ChurchCMS создаёт каталог резервных копий рядом с каталогом сайта:

```
/var/www/churchcms
/var/www/churchcms-backups
```

Копии намеренно не разрешается хранить внутри публичного корня ChurchCMS.

Путь можно переопределить в локальной конфигурации через `operations.backup_path`. Для технической диагностики CLI также принимает `--path=/абсолютный/путь`.

## Что входит в копию

Текущий формат `churchcms-backup-v1` содержит:

- `config/local.php`;
- файлы из `storage/uploads`;
- логический снимок всех обычных таблиц текущей PostgreSQL/MySQL базы;
- `manifest.json` с версией ChurchCMS, временем создания, размерами и SHA-256.

Для БД не требуются внешние `pg_dump` или `mysqldump`. Данные читаются через PDO. Значения строк сохраняются как base64-or-null, чтобы будущий restore мог восстановить в том числе бинарные значения без перекодирования.

Символические ссылки в резервируемых данных запрещены: это исключает случайное копирование файлов за пределами сайта.

## Создание копии

Технический резервный способ:

```bash
php bin/backup.php create
```

Успешной считается только копия, которая прошла проверку манифеста и всех контрольных сумм до финального переименования каталога.

## Повторная проверка

```bash
php bin/backup.php verify 20260926T123456Z-012345abcdef
```

Команда не принимает произвольный путь к копии: идентификатор имеет строгий формат, а корневой каталог задаётся настройкой ChurchCMS.

## Восстановление данных БД

Техническая команда восстановления БД:

```bash
php bin/backup.php restore-db 20260926T123456Z-012345abcdef \
  --confirm=20260926T123456Z-012345abcdef
```

Идентификатор требуется указать дважды намеренно: операция удаляет текущие строки таблиц и возвращает состояние из выбранной копии.

Перед изменением данных ChurchCMS повторно проверяет manifest и SHA-256, требует совпадения драйвера, набора таблиц и столбцов с текущей схемой. PostgreSQL восстанавливается одной транзакцией: таблицы очищаются, строки вставляются в порядке зависимостей внешних ключей, после чего синхронизируются sequence. Для MySQL сохраняется аналогичная проверка схемы и синхронизация auto_increment.

После восстановления повторно проверяется количество строк каждой таблицы. Если PostgreSQL-восстановление завершается ошибкой до commit, транзакция откатывается.

`restore-db` восстанавливает только БД. Файловая часть восстанавливается отдельной командой, чтобы каждая разрушительная операция имела собственную проверку и понятный путь отката.

## Восстановление config и uploads

Техническая команда:

```bash
php bin/backup.php restore-files 20260926T123456Z-012345abcdef \
  --confirm=20260926T123456Z-012345abcdef
```

Перед заменой файлов ChurchCMS повторно проверяет manifest и SHA-256 всей резервной копии. Из копии разрешены только `config/local.php` и файлы под `storage/uploads`; неизвестные пути, повторяющиеся записи и небезопасные относительные пути останавливают операцию до изменения установленного сайта.

Новая конфигурация и новый каталог uploads сначала собираются во временных кандидатах рядом с целевыми путями и повторно проверяются по размеру и SHA-256. Затем текущие файлы переименовываются в rollback-копии, а проверенные кандидаты занимают рабочие пути. Если любой шаг переключения завершается ошибкой, ChurchCMS пытается вернуть прежние `config/local.php` и `storage/uploads`.

Восстановление uploads является точным снимком: файлы, созданные после резервной копии, исчезают после успешного restore. Поэтому команда требует явного повторения идентификатора через `--confirm`.

БД и файловая часть пока восстанавливаются двумя отдельными командами. Единая orchestration «restore/apply/healthcheck/rollback» остаётся следующим этапом update workflow.

## Что пока не реализовано

До закрытия общего пункта Update/backup workflow остаются:

- staging и проверка пакета обновления;
- безопасная замена файлов приложения;
- запуск миграций после замены;
- обязательный healthcheck;
- автоматический откат при неудачном обновлении;
- простой мастер в Admin Shell.

Проверенная резервная копия, восстановление БД и восстановление файлов образуют рабочий фундамент аварийного восстановления. До завершения общего update workflow остаётся объединить эти операции с применением обновления, healthcheck и автоматическим откатом.
